# Docs as Code 与 Agent 交接

用户要求未来 Git 交付同时带文档和可恢复上下文。先遵守目标仓库的 `AGENTS.md` 与既有开发规范；天河项目的具体约定在 `docs/development/docs-as-code.md`。其他仓库可采用等价路径，不要复制天河的发布方式或业务状态。

## 提交与上传

1. 核验实际 Git 根目录、暂存区、相关 diff、目标分支和远端。区分已有工作与本轮范围；尚未获得上传授权时完成可审阅文件与验证，不自行发布。
2. 将文档和实现作为同一交付单元。更新受影响的使用说明、接口合同、配置、部署/运维说明；每个非空提交增加或实质更新一个变更记录。纯文档、测试、依赖、重构提交同样说明意图和验证，不强行改无关业务文档。
3. 记录足以独立接手的信息：问题与验收目标、前后行为、关键文件/接口、已确认决策及理由、准确验证命令与结果、环境与局限、部署/迁移和回退、未完成项及下一条具体行动。短任务可以简写；未执行测试写原因，不能推测通过。
4. 使用 [变更记录模板](assets/change-record.md) 起稿。重要且影响后续工作的架构决策可使用 [ADR 模板](assets/adr.md)，一次记录一个决策，并从变更记录链接；普通改动直接写取舍即可。
5. 任务目标、阻塞、入口或下一步改变时更新稳定交接文档。持久事实放对应主题文档，变更记录只链接，避免复制整段对话和制造多个“最新”入口。明确区分已实现、已验证、拟议和未完成；旧快照保留日期。
6. 审查索引中的最终版本，确认文档确实随同提交，相关链接可用，没有秘密或私有运行数据。运行项目要求的文档检查与适量业务验证；commit body 和 PR 说明链接仓库记录，摘要说明原因与结果。
7. 上传前在实际发布工作区再次检查待推送提交，并针对最终发布快照重跑适用验证；开发工作区混有其他改动时，其测试结果不能直接证明选定发布子集可用。若走净化源码快照，文档、skill、检查规则必须一起同步；不携带被排除的原仓库历史。推送后仅在实际成功时记录远端结果，提交哈希由 Git 提供，不能编造或在本提交中自引用未知哈希。

## 交接内容的准确性

- 记录用户已确认的约束和影响实现的决策，不把推测或未获授权的提案写成承诺。仅当缺失信息实际阻断工作时提问。
- 文档中使用仓库相对路径及可复现命令；机器专属路径、数据目录只在必要的本地说明中标注，不复制凭据。
- 部分暂存时，以索引内容为准。未暂存的文档、聊天中的报告、另一工作区的记录不能满足当前提交要求。
- 交付说明应明确文件已修改、已提交、已推送分别处于哪一步；结构检查通过不等于技术内容正确。
