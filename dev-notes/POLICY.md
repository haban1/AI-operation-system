# 开发上下文与提交交接规范

本目录是受 Git 版本管理的开发资料，供开发者和 Agent 接力。与产品代码、公开产品文档分开；禁止随构建、发布包、镜像、静态站点或整库同步进入非开发环境。它不是存放秘密的地方。

## 开始工作

先读本目录 README、当前分支最近的相关 changes 记录及适用的 decisions。用当前代码、Git 状态和必要的运行检查核实旧记录，不将旧状态当作今天的事实。文档使用仓库相对路径，避免依赖原聊天和个人电脑路径。

## 每次提交

- 每次提交前，在 `changes/` 新增或更新与本次 staged diff 对应的记录，与代码同次提交。记录可以简短，但需包含背景/目标、关键理由、改动入口、验证证据和下一步。拆分提交时逐个对应。
- 没有事实来源的理由写明未知；不要把预期或计划写成完成。只写实际考虑过的方案；代码和已有文档已经解释的内容用引用。
- 分开写代码完成、本地验证、CI、部署、线上验收。验证未运行时说明原因。
- 重要长期决定另写 `decisions/` ADR，标明决定状态、取舍和替代关系；普通小修复保留简短 changes 记录即可。
- 记录时间含时区；用分支、已有基线 SHA 和文件路径建立追踪关系。不要为了在文件中写入其自身 commit SHA 而反复 amend。
- 文档自身的修正无需递归新增记录；保留修正背景。merge/cherry-pick 保留原记录，并补充集成或冲突处理的实际结果。已推送历史缺失记录时后续补记并标注 SHA，不自动改写历史。
- 保留他人的文件和暂存边界；按路径暂存自己的修改。不得因本规范擅自 commit、push、发布或部署。
- 推送前核对所有待推送提交的记录覆盖，不能只看最后一个提交。

## 内容边界

不保存密钥、密码、cookie、token 地址、生产个人数据、完整聊天或未筛选的日志。用最少而足够的业务背景、证据路径和简洁结论。目录隔离不能隐藏仓库中的信息；公开仓库的记录同样公开。

## 构建和部署隔离

首次接入以及构建/部署配置变化时，核对实际链路并将证据写入 changes；未变更的链路可沿用仍适用的既有证据。

1. 不把本目录放入代码资源目录、公开静态目录或文档站发布源；也不建立把它复制进去的符号链接、导入或同步步骤。
2. 本目录需要入 Git，不能用 `.gitignore` 代替部署排除。`export-ignore` 仅保护使用它的 Git 归档，不保护普通 clone、zip、rsync、Docker 或服务器 `git pull`。
3. 检查有效 Docker build context 和对应 ignore 文件、包管理发布配置、压缩/同步脚本、流水线产物上传路径。Dockerfile 专用 ignore 文件可能覆盖根 `.dockerignore`，需逐项检查。
4. 优先仅打包/复制运行所需的明确产物路径。存在整库复制、`COPY . .`、打包根目录、原地 `git pull` 等链路时，要修正有效排除或改成产物交付；删掉最终镜像中的文件不代表先前镜像层没有它。
5. 在实际发布使用的最终产物上检查本目录及其内容没有混入；证据区分配置审查和产物验证。文件名不存在不等于内容没有被生成器复制进别的文件。
6. 若自动部署会将记录带入非开发环境，在修复前不执行会触发该部署的 push/合并/发布。本地准备工作继续，说明具体阻塞与缺失证据。

## 跨 Agent 与强制执行

支持读取仓库指令的 Agent 遵守本规范；无需依赖某个托管平台或专用 skill。

要让所有贡献者受检查约束，需要仓库配置必需的 CI/合并检查，并在所有发布路径的产物上传前检查部署隔离。仅添加本规范或本地 hook 不代表全员强制执行已生效。逐提交检查应覆盖该次事件实际新增的全部提交，而非只检测总 diff 是否有一个 Markdown 文件；首次提交、合并、挑选提交和纯文档修正需有明确处理。
