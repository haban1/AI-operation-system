## 实际链路

```text
微信用户 → 原机器人 → 项目内微信 API → 原微信 Agent
                                      ├─ search_knowledge → 天河已发布知识片段
                                      ├─ 生成答复 → 原机器人发送
                                      └─ 转人工 → 天河新 PostgreSQL → 接待通知与队列

天河知识库页面 → 上传 → 处理 → 测试 → 发布 → 微信检索可见
天河微信客服模块 → 登录验证与服务端代理 → 微信 API → 天河新 PostgreSQL / 原机器人
```

用户明确要求：天河“转人工说法”的标准说法、系统内置匹配和 AI 相似说法不接入微信客服，不通过知识检索接口同步这些规则。微信是否转人工由其自己的 Agent 与 `request_human_handoff` 工具决定。

微信 Agent 保留原多轮工具调用、引用和转人工机制，`search_knowledge` 仅使用天河纯检索接口。天河原有 Agent 和其他渠道流程继续保留。草稿、测试版本不对微信检索开放；无已发布资料时返回 `NOT_READY`，不会退回旧微信知识库。

## 页面与权限

侧栏统一为 **微信客服**，包含 **人工接待 / 好友群发 / 机器人管理** 三个页签。切换时保留群发草稿、好友选择与机器人后台页面状态；隐藏页签暂停接待/群发轮询，离开模块后清理请求与嵌入页面。

- **知识库**：唯一资料上传、测试和发布入口。
- **人工接待**：设置转人工通知人，查看接待队列与最近消息，恢复 AI。实际人工文字接待在微信客户端进行。清库后通知人为空，需要重新设置。
- **好友群发**：好友筛选、文字/图片预览、发送确认、进度与最近 30 条记录。请求 ID 防止同一提交重复排队；提交异常后先核对任务记录。
- **机器人管理**：内嵌 `http://127.0.0.1:8080`，使用原后台登录密钥，并提供独立窗口入口。可在 `compose.wechat.yaml` 修改 `WECHAT_ROBOT_ADMIN_URL`。
- 微信 API 的旧文档/检索管理接口在集成模式下关闭。访问 8000 首页跳转天河。
- 管理员 Cookie 留在天河，管理凭据由服务端持有。代理仅开放指定管理接口；检索凭据不能管理知识。
- 顶部五平台总开关不控制微信；微信自动回复开关在 `.env.wechat` 中，模型使用天河「企微及 AI」配置。

## 日常容器开发

在 `project` 目录执行：

```powershell
docker compose -f compose.yaml -f compose.wechat.yaml up -d --build --wait --wait-timeout 240
docker compose -f compose.yaml -f compose.wechat.yaml ps
# 修改服务端后重启对应服务；前端修改后刷新浏览器
docker compose -f compose.yaml -f compose.wechat.yaml restart wechat web rag
```

当前 `tianhe-dev` 分组包含 `web`、`rag`、`wechat`、`wechat-db` 四个服务。应用源码挂载自本项目；微信 API 使用 `Dockerfile.tianhe`。机器人底层仍通过外部 `wechat-robot` 网络连接，原回调别名 `customer-service-api:8000` 和回调路径不变。

停止并保留数据库：

```powershell
docker compose -f compose.yaml -f compose.wechat.yaml down
```

不要在日常停止时加 `-v`；该参数会删除天河的数据卷。

## 机器人重新部署后的必做步骤（2026-10-14 补充）

微信机器人每次重新部署（重扫码 / 重置实例）会生成**新的随机实例 ID**，这个 ID 同时决定三样东西：

- 容器名：`client_<实例ID>` / `server_<实例ID>`；
- 宿主机目录：`.deploy/local/wechat-robot/<实例ID>/`；
- MySQL 库名：`<实例ID>`（即 **一个全新的空库**）。

因此重新部署后**上一轮的 AI 配置、好友设置、知识、会话全部不在新实例里**，必须按下面顺序补齐，否则会出现「能扫码登录、能收消息，但机器人不回复」或「天河微信客服页报错」。

1. **同步天河侧的机器人地址**（否则微信客服页好友/群发/接待直接 502）
   把 `project/.env.wechat` 的 `WECHAT_ROBOT_BASE_URL` 改成 `http://client_<新实例ID>:9000`，然后
   `docker compose -f compose.yaml -f compose.wechat.yaml up -d wechat`。
   典型症状：`tianhe-dev-wechat-1` 日志出现
   `WechatRobotClientError: WeChat robot API request failed: [Errno -2] Name or service not known`。
   取当前实例 ID：`docker ps --format '{{.Names}}' | grep '^client_'`。

2. **在机器人后台配置 AI**（否则只收消息不自动回复）
   入口 `http://127.0.0.1:8080`（天河内：工作空间 → 微信客服 → 机器人管理，内嵌打开）。
   新实例的 `global_settings` 只有**一行出厂占位值**，需要逐项改成真实配置：

   | 字段 | 新实例默认值 | 说明 |
   |---|---|---|
   | `chat_ai_enabled` | `0`（关） | 必须置为开 |
   | `chat_base_url` | `https://new-api.houhoukang.com/` | OpenAI 兼容模型地址 |
   | `chat_api_key` | `sk-123456`（假值） | 必须换成有效密钥 |
   | `chat_model` | `gpt-4o-mini` | 模型名 |
   | `chat_prompt` | `你是一个聊天机器人。` | 客服人设，建议重写 |
   | `text_embedding_model` | 空 | 需向量检索时填写 |

   保存时的校验要求 `ChatAPIKey` / `ChatBaseURL` / `ChatModel` / `ImageRecognitionModel` / `ChatPrompt` 均非空
   （`controller/global_settings.go:42`）。未配置时 client 启动日志会打印
   `[RAG] AI 配置未设置（ChatBaseURL/ChatAPIKey/TextEmbeddingModel），RAG 服务跳过初始化`。

3. **在天河重新设置转人工通知人**（微信客服 → 人工接待）。清库后该值为空，转人工时无人收到通知。

4. **在天河知识库上传并发布资料**。未发布时微信检索返回 `NOT_READY`，Agent 没有可引用的依据。
   流程：知识库 → 上传 → 处理 → 测试 → 发布。

5. **在微信里给机器人发一条消息验证**（机器人不会回复自己的消息，需用其他微信号发）。

上面 1、3、4 步可以一键核对（在 `project` 目录，用项目自带 Node 24）：

```bash
PATH="$PWD/runtime:$PATH" node outputs/qa-20261014-wechat/check-wechat-status.mjs
```

脚本会比对「配置的机器人地址 vs 实际 client 实例」、读取好友、检查通知人 / 知识资料 / 发布版本 / 群发接口，
并逐项标出还差什么。它不覆盖第 2 步（机器人后台的 AI 配置在机器人自己那边，脚本只做提醒）。

### 天河侧微信客服 API 的现状（2026-10-14 实测）

`.env.wechat` 中给 `wechat-assistant` 用的模型凭据当前不可用，需要有效密钥：

- `DASHSCOPE_API_KEY`（`sk-1f1…`，67 字符）对官方 `dashscope.aliyuncs.com` 与配置的中转站
  `cs.jaspervault.pro` 均返回 `401 INVALID_API_KEY`。该 key 非空，因此 `LlmClient.enabled` 为真
  （`app/llm/client.py:32`），调用会真的发出并失败，影响 `wechat-assistant` 的生成类能力。
- `DASHSCOPE_EMBEDDING_API_KEY` 为**空**，但 `DASHSCOPE_EMBEDDING_BASE_URL` 有值 ——
  `app/llm/client.py:162` 的取值逻辑是「只要配置了 embedding 的 URL 或 KEY，就返回 `embedding_api_key`」，
  于是拿到空 key，`EmbeddingClient.enabled`（`client.py:118`）为假，`embed()` 直接返回 `None`：
  **向量检索被静默跳过**（不报错、无日志），FAQ 语义匹配退回纯文本匹配。
  要么补齐 `DASHSCOPE_EMBEDDING_API_KEY`，要么把 `DASHSCOPE_EMBEDDING_BASE_URL` 与
  `DASHSCOPE_EMBEDDING_API_KEY` **同时清空**，让它回退到 chat key。

天河自己的 RAG 检索（`rag-service`）走本地 fastembed（`RAG_FASTEMBED_LOCAL_FILES_ONLY=true`），
不依赖上述 key，因此知识检索本身是自洽的。
