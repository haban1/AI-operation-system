# GitHub 最新 main 本机部署

时间：2026-11-09，Asia/Shanghai。部署主线：`bd66d8f359c377ad2cad8add5a2fe1eb33638728`。

## 背景与目标

用户要求拉取 GitHub 最新 main 并部署到现有本机服务。这次授权部署正式代码，
此前的 44 页精简界面仍为独立预览，没有据此替换实际界面。

## 变更与影响

集成最新运营 RAG、回答风格、累计五次澄清及口语查询与重排对齐。部署使用原有
`tianhe-dev` Compose 项目及三个配置文件，仅重建 Web、RAG 容器；保留数据卷、
知识发布版本、BGE 模型目录、模型密钥、原生微信服务和内容工作台。

本机有既有未提交修复。以净化源码 `631bf45` 为共同内容基线做文件级三方集成，
保留评论详情邀约与确认、自然回复风格、界面控件和采集相关修复，不覆盖原 Git 历史。
隔离候选共核对 1,153 个源文件，解决 8 个重叠；实际应用 38 个文件（27 个已有、11 个新增）。
部署并非完全纯净的上游快照，仍含本机既有修复，文件指纹留在本机部署资料中。

## 决策与取舍

普通 Git HTTPS 连接超时，改用 GitHub REST API 读取最新提交及 Git 对象，逐个核对
blob、tree、commit 的真实 SHA，完成连通性检查后才更新 `origin/main`。切换前再次认证读取
远端 main，确认仍为上述 SHA。没有将源码 ZIP 伪称为 Git 提交，也没有推送其他远端。

本机 `RAG_QUERY_REWRITE_ENABLED=false` 会让最新查询修复不生效，部署时改为 `true`，
其余模型、知识与证据阈值保持原配置。依赖锁文件未变，复用原镜像与只读源码挂载。

兼容检查发现“我可以去你们公司…”的口语前缀被当成机构名而误拒标准问句。
`query_rewrite.py` 仅扩充可剥离的来访前缀，不放宽机构、数字、否定或事实约束；
补充 4 个正反例，保证真实机构不能被替换。本机旧评论回归迁移到新 canonical 协议，
原回答风格测试显式传入不可变展示配置。本次新增兼容补丁也随本地集成提交保存。

## 部署与回退

本机部署资料位于被 Git 忽略的 `.codex-work/deploy-main-20261109/`：保存上游拉取回执、
候选代码、文件指纹、前后健康记录、测试日志及回退脚本。`backup/` 包含原源码/配置、
停止写入后复制的主库和 WAL/SHM，以及完整 RAG 数据归档；这些含私有运行数据，不能入 Git。
备份未执行还原演练。其余约 3.1 GiB 业务媒体继续保留原卷，不做清理或覆盖。

使用原 `compose.yaml`、`compose.wechat.yaml`、`compose.workbench.yaml`：先停止 Web/RAG，
完成一致性备份，再应用候选源码与开关，按 RAG、Web 顺序 `up -d --no-deps`。
未删除数据卷或旧镜像，未重启原生微信协议/客户端、Signal 或外部创作工具。
实际检查 Web/RAG 容器不存在 `dev-notes`、skill 或精简设计目录，开发资料不进入运行服务。

需要代码回退时，在本机 project 目录停止 Web/RAG，运行
`node .codex-work/deploy-main-20261109/rollback-source.mjs`，再用相同三个 Compose 文件
重新创建 RAG 和 Web。脚本先校验文件指纹，恢复原源码与改写开关，不自动覆盖数据库。
仅发生确认的数据损坏时才另行停写、保存当前库并评估恢复运行数据备份，避免丢失新增消息。
