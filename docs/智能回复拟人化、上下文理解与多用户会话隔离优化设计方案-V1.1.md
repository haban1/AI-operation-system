## 1. 文档目的

当前平台已经可以完成知识库召回、Qwen 语义匹配、受知识约束的回复生成、问候引导、多问题拆分、知识缺口提示和用户主动转人工等流程。但实际聊天中仍存在以下体验和安全问题：

1. 回复过于书面、固定，容易让用户感觉是 AI 或模板机器人；
2. 当前单问题生成只看到本条消息和一条知识，不能自然承接“那收费吗”“地址呢”等追问；
3. 如果直接加入整段历史上下文，Qwen 可能受到旧话题干扰；
4. 用户突然切换话题时，系统必须以当前消息为准，不能继续沿用旧主题；
5. 多个用户同时咨询时，必须保证上下文、知识匹配、回复任务和实际发送目标互不串台；
6. 视频号私信页面当前未稳定取得用户 ID，也没有正式采集头像，不能把昵称当作唯一身份；
7. 转人工时必须保留昵称、消息入口、时间和原消息，让人工能够准确找到对应用户。

本方案将上述问题整合为一套完整的运行架构，目标是：

> 知识库负责保证“说什么是对的”，Qwen 负责理解“用户现在想问什么”和“怎样表达更自然”，系统负责保证“这条回复属于哪个用户、发到哪个会话”。

## 2. 当前实现核对结果

本节只描述当前源码已经存在的真实能力，不把建议方案写成已实现功能。

### 2.1 当前知识回复生成

当前 `src/services/qwen.js` 的 `composeReply()`：

1. 只向 Qwen 提供当前用户消息、唯一命中知识的问题和答案；
2. `temperature` 当前为 `0.1`；
3. 提示词要求知识库标准答案逐字、完整出现在回复中；
4. 不提供最近聊天上下文；
5. 不区分评论区和私信的自然表达风格。

`src/services/decision.js` 的 `validateReply()` 还会检查生成内容是否完整包含标准答案。因此现有回复安全性较高，但知识答案如果较正式，最终回复也会显得正式和机械。

### 2.2 当前多问题和固定话术

`src/services/conversation-intent.js` 当前已经支持：

- 纯问候检测；
- 显式“转人工”命令判断；
- 多问题拆分；
- 知识缺口话术；
- 多问题固定拼接。

当前多问题主要使用：

```text
关于你提出的问题：

1. 标准答案

2. 标准答案
```

问候、转人工、无法确认也主要是单套固定话术，因此重复使用时容易出现明显模板感。

### 2.3 当前会话区分方式

`src/server.js` 的 `messageConversationKey()` 当前会组合：

- 平台代码；
- 运营账号 ID；
- 消息类型；
- `conversationId`、`chatId`、`sessionId`、`userId`、`senderId` 等可用字段；
- 如果均不存在，可能退化使用 `user_name`；
- 最后可能退化为 `unknown`。

方向是正确的，但昵称和 `unknown` 不能作为多人长期上下文的可靠身份依据。

### 2.4 当前转人工通知

`src/services/manual-notification.js` 当前已经在通知标题和正文中带上用户昵称，例如：

```text
【视频号·私信】张先生需要转人工
用户名称：张先生
消息来源：私信
私信内容：“……”
```

因此本方案不会删除昵称。后续只是在昵称之外增加更可靠的系统会话身份和人工定位信息。

### 2.5 当前视频号私信采集

当前视频号代码已经：

- 区分“私信”和“打招呼消息”；
- 识别可见未读红点；
- 采集昵称、消息预览、消息时间；
- 尝试从 DOM 中读取 `data-conversation-id`、`data-session-id`、`data-chat-id`、`data-id`、`id` 等内部会话标识；
- 将可用标识保存到 `context.conversationKey`。

当前尚未正式实现：

- 视频号私信用户头像采集；
- `avatarUrl`；
- `avatarHash`；
- 稳定的视频号用户 ID；
- 无会话 ID 时的长期可靠身份合并。

因此，头像只能作为后续增强方向，不能作为当前已经可用的身份依据。

## 3. 设计目标与非目标

### 3.1 核心目标

1. 单问题回复更像真实社区运营人员，简短、自然、友好；
2. 不因拟人化而新增、改错时间、费用、地址、政策、条件或承诺；
3. 只有当前消息信息不完整时才使用上下文；
4. 当前消息包含完整新问题时，旧上下文不能覆盖当前意图；
5. 对话存在歧义时主动确认，不强行猜测；
6. 同一用户消息串行处理，不同用户可以并行处理；
7. Qwen 只能生成文字和意图判断，不能决定回复发给谁；
8. 昵称始终记录、展示，并在转人工通知中保留；
9. 视频号没有稳定用户 ID 时，按身份可信度分级处理；
10. 生成回复期间如果用户又发新消息，旧回复必须失效或重新合并；
11. 身份不足、目标不唯一、页面核验失败时禁止自动发送；
12. 所有改造必须保留现有知识库平台隔离和风险门禁。

### 3.2 非目标

第一阶段暂不做：

- 不让 Qwen 自由脱离知识库回答；
- 不直接把温度提高到高随机值；
- 不依靠随机添加“亲、哈、哦、表情”冒充拟人化；
- 不用昵称单独作为长期唯一用户 ID；
- 不把视频号私信和打招呼消息仅凭同名自动合并；
- 不在身份为低可信时使用长期上下文；
- 不一次性将全部历史聊天发送给 Qwen；
- 不自动触发真实平台测试消息或真实回复。

## 4. 总体架构

建议将回复链路拆为七层：

```text
平台消息采集
    ↓
会话身份与消息归属层
    ↓
短时消息聚合与会话版本层
    ↓
当前问题/上下文意图解析层
    ↓
知识召回与事实锁定层
    ↓
自然话术选择与拟人化编排层
    ↓
发送前会话、目标和页面核验层
```

每一层只做自己的职责：

- 身份层不能生成答案；
- Qwen 不能选择发送目标；
- 上下文只负责补全问题，不负责提供事实；
- 知识库只决定可使用的事实；
- 拟人化层只能改变表达，不得改变事实；
- Agent 只能向服务端已经绑定的目标会话发送。

## 5. 回复拟人化设计

### 5.1 当前“AI味”的主要来源

1. 标准答案必须原文完整包含；
2. 多问题固定使用编号模板；
3. 问候、转人工、知识缺口只有单套话术；
4. 不区分评论和私信口吻；
5. 不知道前面已经问候或回答过什么；
6. 知识库标准答案本身偏公告和书面表达；
7. 生成温度低，句式变化很少。

### 5.2 事实层与表达层分离

建议一条知识同时维护：

```text
标准问题
标准答案
必须保留事实
允许改写内容
自然回复话术
```

示例：

```text
标准问题：参加社区活动需要收费吗？

必须保留事实：
1. 是否收费以具体活动公告为准；
2. 公告未明确收费时不要先转账；
3. 可以私信工作人员确认。
```

允许生成的自然回复：

```text
这个要看具体活动公告哈。公告没写收费的话先别急着转账，可以先私信我们确认一下。
```

禁止生成：

```text
活动都是免费的。
```

### 5.3 自然回复话术库

建议新增每条知识的审核话术，例如：

- 稳妥版；
- 自然亲切版；
- 简洁版；
- 评论区版；
- 私信版；
- 简体版；
- 繁体版。

Qwen 在知识保存或运营人员点击生成时，生成 5～8 条候选话术。运营人员可以：

- 勾选启用；
- 手工修改；
- 设置默认话术；
- 标记评论或私信适用；
- 禁用不满意话术；
- 重新生成。

运行时优先使用已经审核启用的话术。没有启用话术时回退到标准答案，不能因为拟人化任务失败而影响知识回复可用性。

### 5.4 评论和私信差异

评论区：

- 默认 1～2 句；
- 直接回答；
- 尽量不重复用户问题；
- 不每次都加问候和结尾；
- 严格遵守平台长度限制。

私信：

- 可以 1～3 句；
- 允许自然承接上文；
- 可以引导用户补充活动名称等必要信息；
- 同一会话不重复问候；
- 不每条都说“如果还有问题欢迎咨询”。

### 5.5 多问题自然编排

两个简短问题优先自然合并，不强制编号：

```text
收费情况要看具体活动公告，公告没写收费的话先别转账。至于能不能带孩子，我这边暂时确认不了，需要人工确认的话请输入“转人工”。
```

三个以上、答案较长或条件较多时才分点：

```text
关于你提到的几个问题：

1. ……
2. ……
3. ……
```

保留用户已经确认的要求：多问题开头不重复原问题，使用“关于你提出的问题”或更自然的等价表达。

### 5.6 AI味发送前检查

增加语言检查器，检查：

- “根据您提供的信息”；
- “综上所述”；
- “希望以上回答对您有所帮助”；
- 重复问候；
- 重复用户原问题；
- 无意义固定结尾；
- 简单问题回复过长；
- 模板堆叠；
- 新增知识库中不存在的事实。

语言检查只能调整表达，不能改动事实锁定字段。

## 6. 上下文理解与抗干扰设计

### 6.1 核心原则

```text
当前消息优先；
上下文只补全省略信息；
上下文不能推翻当前消息；
上下文不能充当知识事实；
存在歧义时先询问确认。
```

### 6.2 当前消息独立判断

完整问题示例：

```text
我想问一下，你们的视频可以转载吗？
支付宝怎么转账？
怎么联系社区工作人员？
```

这些问题当前句已经包含明确对象和意图，应直接作为新问题处理，旧活动上下文不能覆盖。

依赖上下文的短句示例：

```text
那收费吗？
地址呢？
什么时候开始？
孩子可以吗？
这个怎么取消？
还要准备什么？
```

只有这类信息不完整的消息，才允许读取最近相关上下文。

### 6.3 话题切换与纠正信号

以下表达优先判定为话题切换或用户纠正：

```text
不是这个
我不是问报名
我说的是
换个问题
另外问一下
先不说这个
我想问的是
```

当前问题完整且与旧主题语义距离较大时，也应自动切换话题。

### 6.4 最小上下文窗口

不发送整个历史记录，只提供：

- 最近 2～4 轮同一会话消息；
- 最近已回答问题；
- 当前活动主题；
- 尚未解决问题；
- 必要的引用消息 ID。

超过设定时间、已经明确切换话题或主题已结束时，不继续继承旧上下文。

建议初始有效期：

- 5 分钟内：强关联候选；
- 5～30 分钟：结合内容判断；
- 超过 30 分钟：默认不直接继承，需要当前消息自己说明或询问确认。

时间只是辅助，最终仍以内容和会话状态为准。

### 6.5 两阶段 AI

第一阶段只做意图解析，输出严格 JSON，不直接生成答案：

```json
{
  "currentMessageComplete": false,
  "needsContext": true,
  "topicSwitched": false,
  "resolvedQuestion": "社区志愿者活动是否收费",
  "referencedMessageIds": [205, 206, 208],
  "subQuestions": ["社区志愿者活动是否收费"],
  "confidence": 0.94,
  "reason": "用户使用‘那’承接上一轮志愿者活动"
}
```

第二阶段在知识已经命中、事实已经锁定之后，才组织自然回复。

### 6.6 双路匹配

每条问题同时比较：

1. 当前消息独立匹配结果；
2. 上下文补全后的匹配结果。

选择规则：

- 当前消息独立匹配置信度高：优先当前消息；
- 当前消息不完整、补全后置信度明显提高：允许使用上下文；
- 两路都高但命中不同知识：询问用户确认；
- 两路都低：进入知识缺口，不强行猜测。

### 6.7 上下文置信度

建议：

- `>= 0.85`：可自动继承并回答；
- `0.65～0.85`：只有唯一主题时允许，否则先澄清；
- `< 0.65`：不继承，不自动猜测。

阈值后续根据真实消息回放测试调整。

### 6.8 多问题逐题处理

用户消息：

```text
那这个收费吗？另外你们的视频可以转载吗？
```

必须拆成：

1. “那这个收费吗”——需要活动上下文；
2. “你们的视频可以转载吗”——当前问题完整，不继承活动上下文。

不能对整条消息统一套用一个旧主题。

## 7. 多用户并发会话隔离设计

### 7.1 Qwen 的边界

Qwen 每次只能看到系统本次发送的内容。跨用户串台通常不是模型主动看到其他用户，而是系统查询、任务绑定或页面发送目标发生错误。

因此隔离必须依靠：

```text
稳定会话键
+ 数据库范围限制
+ 每会话队列
+ 任务目标绑定
+ 发送前页面核验
```

不能只靠提示词写“不要混淆用户”。

### 7.2 会话唯一命名空间

私信优先使用：

```text
平台 + 运营账号 + 平台会话ID/对方用户ID
```

评论优先使用：

```text
平台 + 运营账号 + 帖子ID + 根评论ID + 发言者平台ID
```

同一个用户在不同帖子下评论时，评论上下文默认分开，避免把不同作品的问题混在一起。

### 7.3 昵称的正确用途

昵称必须保存，用于：

- Web 展示；
- 人工通知；
- 搜索和人工定位；
- 页面发送前辅助核验。

昵称不能单独用于：

- 长期唯一会话 ID；
- 同名用户自动合并；
- 跨私信入口合并；
- 决定回复发送目标。

### 7.4 每会话串行、跨会话并行

```text
用户甲：甲1 → 甲2 → 甲3
用户乙：乙1 → 乙2
用户丙：丙1 → 丙2
```

甲、乙、丙可以同时处理，但同一会话内部必须按顺序处理。实现方式可采用：

- `conversation_id` 分区队列；
- 每会话互斥锁；
- 每会话版本号；
- 任务租约和超时回收。

### 7.5 上下文查询强制范围

只允许：

```sql
SELECT *
FROM messages
WHERE conversation_id = ?
ORDER BY sequence_no DESC
LIMIT ?;
```

禁止使用全局“最近消息”作为上下文：

```sql
SELECT *
FROM messages
ORDER BY created_at DESC
LIMIT ?;
```

### 7.6 回复任务绑定

每个任务至少绑定：

```json
{
  "replyJobId": 9001,
  "messageId": 208,
  "conversationId": 35,
  "conversationVersion": 16,
  "platformCode": "wechat_channels",
  "accountId": 3,
  "targetPlatformUserId": null,
  "targetConversationKey": "abc123",
  "targetDisplayName": "张先生",
  "inboxType": "GREETING"
}
```

Qwen 无权修改这些目标字段，只能返回回复文字、意图和引用消息 ID。

### 7.7 生成期间新消息处理

生成开始时记录：

```text
conversationVersion=16
latestMessageId=208
```

发送前重新检查。如果同一会话已经变成版本 17 或最新消息 209：

1. 旧回复任务标记为 `STALE`；
2. 不发送旧结果；
3. 合并新消息后重新拆分、匹配和生成；
4. 不能把最新消息标记为已读或已处理却没有回答。

其他用户的新消息不影响本会话任务。

### 7.8 发送前目标核验

Agent 在真实页面发送前必须核对：

- 平台；
- 当前运营账号；
- 私信/打招呼入口；
- 会话内部标识；
- 昵称；
- 当前最新用户消息；
- 任务绑定的原消息；
- 页面是否存在多个同名候选。

目标不唯一或任一关键字段冲突时，停止发送并返回 `TARGET_IDENTITY_UNCERTAIN`。

## 8. 视频号无稳定用户 ID 的身份方案

### 8.1 事实边界

当前系统能采集昵称、消息预览、时间、未读状态、入口类型，并尝试读取 DOM 内部 `conversationKey`。当前没有正式头像采集，也没有稳定视频号用户 ID。

### 8.2 身份分级

#### HIGH：高可信

满足任一：

- 页面内部稳定 `conversationKey`；
- 网络请求或组件数据中的稳定联系人/会话 ID；
- 可跨刷新、跨排序重新定位的稳定线程键。

允许：

- 长期上下文；
- 自动连续回复；
- 重启后继续识别；
- 私信发送前按稳定键定位。

#### MEDIUM：中可信

在后续实现头像采集后，可使用：

```text
运营账号 + 消息入口 + 昵称 + 头像哈希
```

允许：

- 短期上下文；
- 发送前严格核验；
- 不自动跨入口合并；
- 不在存在多个候选时自动发送。

#### LOW：低可信

只有：

- 昵称；
- 最新消息；
- 时间；
- 私信/打招呼入口。

只允许：

- 记录和展示消息；
- 生成转人工通知；
- 当前页面保持不变且目标唯一时进行受限单轮处理；
- 不使用长期历史上下文；
- 不将同名用户合并；
- 页面重新排序、重启或目标不唯一时禁止自动发送。

### 8.3 头像后续采集

头像是增强信号，不是当前能力。后续需要新增：

- `avatar_url`；
- `avatar_hash`；
- 头像采集来源；
- 头像最后更新时间；
- 头像是否可稳定重取。

头像也不能单独作为绝对用户 ID，因为用户可能更换头像；应与昵称、入口和其他会话证据组合使用。

### 8.4 私信与打招呼消息合并

只有稳定会话标识一致时才自动合并。若只有相同昵称，不自动合并，分别显示：

```text
张先生｜私信
张先生｜打招呼消息
```

转人工通知必须明确写明入口。

## 11. AI 接口设计

### 11.1 意图解析接口

输入仅包含同一会话经过筛选的最近消息和当前消息。输出严格 JSON：

```json
{
  "conversationId": 35,
  "currentMessageId": 208,
  "currentMessageComplete": false,
  "needsContext": true,
  "topicSwitched": false,
  "resolvedQuestion": "社区活动是否收费",
  "referencedMessageIds": [205, 206, 208],
  "subQuestions": [
    {
      "text": "社区活动是否收费",
      "needsContext": true
    }
  ],
  "confidence": 0.94
}
```

服务端验证引用消息必须全部属于同一 `conversation_id`，否则结果作废。

### 11.2 自然回复接口

输入：

- 当前用户表达；
- 消息类型；
- 最近必要上下文；
- 已锁定知识；
- 必须保留事实；
- 已审核话术；
- 平台长度限制；
- 语言脚本：简体或繁体；
- 当前会话是否已问候。

输出：

```json
{
  "replyText": "这个要看具体活动公告哈。公告没写收费的话先别急着转账，可以先私信我们确认一下。",
  "usedKnowledgeIds": [12],
  "usedVariantIds": [88],
  "addedFacts": [],
  "style": "NATURAL_FRIENDLY",
  "confidence": 0.96
}
```

服务端不能只相信 `addedFacts`，还需要基于必须保留字段、禁用表达和风险规则做独立校验。

### 12.4 “小智”知识库即时回复测试台

#### 12.4.1 产品定位和命名

平台内原本设想的“小管家”统一命名为：

```text
小智
```

第一阶段只承担一个明确作用：

> 让运营人员在上传、编辑或发布知识后，直接用真实聊天方式测试系统会怎样理解问题、命中哪条知识、生成什么回复。

“小智”不是第六个真实运营平台，不负责采集外部消息，也不负责把回复发送到抖音、视频号、微博、小红书或 B 站。它是平台内部的知识库回复测试台。

当前前端还没有正式的“小管家”页面。实施时在左侧导航栏新增独立入口，名称只显示“小智”，建议放在“相似问法库”下方，便于运营人员完成知识维护后立即进入测试：

```text
知识库
相似问法库
小智
评论与私信
```

页面副标题建议为：

```text
知识库回复效果即时测试
```

知识导入成功页、知识编辑保存成功提示中，可额外提供“去小智测试”快捷按钮，但左侧导航入口必须长期保留。

#### 12.4.2 为什么不能沿用五平台轮询

五个平台的正式回复链路需要经过：

```text
平台页面采集
→ 轮询发现新消息
→ Local Agent / RPA 领取
→ 知识判断
→ 生成回复
→ 打开真实聊天窗口
→ 发送并回传状态
```

这套流程必须考虑平台登录、页面状态、采集周期、发送锁和风控，因此天然存在等待时间。

“小智”不需要等待外部平台出现新消息。运营人员点击发送后，Web 应立即调用服务端测试接口：

```text
运营人员输入问题
→ Web 立即 POST 请求
→ 服务端直接运行正式知识判断与回复生成逻辑
→ 当前请求直接返回结果
→ Web 立即显示回复
```

明确禁止“小智”经过以下环节：

- 平台启停开关；
- 五平台消息轮询；
- Local Agent；
- Playwright 或 RPA；
- 平台登录状态检查；
- 正式消息发送队列；
- 企微转人工通知；
- 真实评论或私信发送。

因此“小智”的“秒回复”指收到 Web 请求后立即开始处理，没有人为设置的轮询等待。完全匹配、相似问法精确匹配和本地规则判断目标在 1 秒内显示；需要调用 Qwen 做语义理解或自然改写时，通常在数秒内返回。AI 网络耗时不能承诺绝对低于 1 秒，但不能再叠加五平台轮询周期。

#### 12.4.3 必须复用正式回复核心

“小智”不能另写一套简化版问答逻辑，否则会出现：

```text
小智测试能回复
→ 真实平台却匹配不到
```

或：

```text
小智回复很自然
→ 真实平台仍然使用旧模板
```

正确结构是把正式回复核心抽成与平台无关的统一服务，例如：

```text
reply-engine
├─ 会话意图判断
├─ 问候与引导
├─ 多问题拆分
├─ 上下文补全
├─ 话题切换
├─ 知识候选召回
├─ 精确问题/相似问法匹配
├─ Qwen 语义判断
├─ 自然回复生成
├─ 长度与事实校验
└─ 最终决策
```

五个平台和“小智”共同调用这个 `reply-engine`，只更换输入来源和输出方式：

| 场景 | 输入来源 | 输出方式 |
|---|---|---|
| 五平台正式回复 | Agent 采集的真实评论或私信 | 进入发送队列，由 Agent 发到真实平台 |
| 小智测试 | 运营人员在 Web 输入的测试消息 | HTTP 请求直接返回，只显示在测试页面 |

这样运营人员在“小智”看到的结果，才真正代表正式平台后续会采用的知识匹配和回复逻辑。

#### 12.4.4 测试知识范围

运营人员通常在“刚上传、还没正式发布”时就需要验证，因此“小智”应支持两种知识范围：

1. **正式知识库**：只使用状态为 `PUBLISHED` 的知识，模拟当前真实平台实际可用内容；
2. **本次上传批次预览**：允许额外读取运营人员明确选择的当前导入批次草稿，用于发布前验证。

当测试包含草稿时，聊天窗口顶部必须显示明显提示：

```text
当前为草稿预览测试。测试结果不会发送到真实平台，草稿发布后才会用于正式自动回复。
```

草稿范围必须绑定明确的 `import_batch_id` 或选中的知识 ID，不能把数据库中所有人的全部草稿都混入测试。正式五平台回复仍然只能使用已发布知识，不能因为“小智”测试过草稿就自动放开。

#### 12.4.5 平台和场景模拟

虽然“小智”不连接真实平台，但回复长度、语气和知识范围可能与平台、消息类型有关。页面顶部应提供模拟条件：

- 知识范围：正式知识库 / 本次上传批次；
- 模拟平台：公共、抖音、视频号、微博、小红书、B站；
- 消息类型：私信 / 评论；
- 回复脚本：自动、简体、繁体；
- 是否启用上下文测试。

默认建议使用：

```text
正式知识库 + 公共场景 + 私信 + 自动识别文字脚本 + 上下文开启
```

选择某个平台时，必须复用该平台真实的知识隔离、回复长度和回复政策，不能跨平台召回不允许使用的知识。

#### 12.4.6 对话页面

建议页面采用三部分：

1. **顶部测试条件栏**：知识范围、批次、平台、评论/私信、简繁体；
2. **中间聊天区**：运营人员消息和“小智”回复，支持连续追问；
3. **右侧或折叠诊断区**：显示本次匹配和生成依据。

聊天区至少提供：

- 输入框；
- 发送按钮；
- Enter 发送、Shift+Enter 换行；
- “新建测试”或“清空上下文”；
- 正在判断/正在生成提示；
- 请求耗时；
- 重新测试；
- 复制回复。

建议“小智”的第一句为：

```text
你好，我是小智。你可以把用户可能会问的问题发给我，我会按当前知识库和所选平台规则模拟回复。
```

#### 12.4.7 诊断结果

“小智”不能只显示最终文案，还要帮助运营人员判断知识库哪里需要调整。每次回复应允许展开查看：

```text
处理结果：可自动回复 / 知识不足 / 需要澄清 / 建议转人工 / 技术异常
命中方式：标准问题 / 相似问法 / 本地语义召回 / Qwen语义判断
命中知识：#12 参加社区活动需要收费吗
知识范围：公共知识库 / 视频号知识库 / 当前导入批次
置信度：0.94
判断原因：用户询问活动是否收费
最终回复：……
总耗时：1.8秒
```

如果没有命中，应显示“为什么没命中”和候选知识，而不是只显示“无法回复”。如果命中但被风险规则拦截，也应明确区分“知识命中成功”和“发送策略不允许自动回复”。

诊断信息仅提供给登录后的运营人员，不能混入实际回复文本。

#### 12.4.8 会话上下文隔离

每次打开“小智”对话生成独立的 `test_session_id`。同一测试会话可以验证连续追问：

```text
运营：社区活动怎么报名？
小智：……
运营：那收费吗？
小智：……
```

点击“新建测试”后必须创建新会话，旧上下文不得继续影响新问题。不同运营人员、不同浏览器标签页和不同测试会话之间都不能共享上下文。

“小智”会话与真实平台用户会话必须使用不同命名空间：

```text
TEST:xiaozhi:{operatorId}:{testSessionId}
REAL:{platform}:{accountId}:{conversationKey}
```

严禁“小智”的测试问题写入真实 `messages` 表后触发：

- 自动回复任务；
- 知识缺口正式工单；
- 企微人工通知；
- 平台发送；
- 真实消息统计。

测试记录如需保留，应使用独立的 `knowledge_test_sessions`、`knowledge_test_messages` 表，或第一阶段只保存在当前浏览器会话中。

  "message": "这个活动可以带孩子吗？",

示例输出：

```json
{

  "decision": "KNOWLEDGE_GAP",
  "matchedKnowledgeIds": [],

  "reason": "当前测试知识范围内没有能够确认儿童参加条件的知识",

```

服务端必须自行根据登录身份、知识状态、平台范围和批次归属重新校验，不能信任浏览器直接传入的知识 ID 列表。

#### 12.4.10 响应速度和异常处理

性能目标：

| 路径 | 页面目标 |
|---|---|
| 标准问题或相似问法精确命中 | 1秒内 |
| 本地召回即可决定 | 1秒内 |
| 需要 Qwen 语义判断或自然生成 | 收到请求后立即执行，通常数秒内 |
| AI超时 | 15秒内给出明确提示并允许重试 |

为改善感知速度，点击发送后应立即把运营人员消息显示到聊天区，并显示“小智正在判断……”，不能等整个请求结束后才渲染用户消息。

第一版可使用普通 `POST` 直接返回完整结果，不需要轮询。如果后续需要逐字输出，可增加 SSE 流式返回，但流式展示不能改变最终事实校验和决策结果。

AI不可用时：

- 能精确命中标准问题或已启用相似问法的，仍可返回受控标准答案；
- 必须依赖AI才能判断的，显示“AI服务暂时不可用，本次测试未完成”；
- 不触发真实转人工通知；
- 不用不受约束的自由生成内容冒充测试结果。

#### 12.4.11 权限和安全边界

“小智”页面只允许已登录运营人员使用，并沿用现有后台权限。接口必须限制单次消息长度、请求频率和并发数，避免误操作或重复点击造成大量 AI 调用。

无论测试结果如何，“小智”都不得：

- 修改知识状态；
- 自动发布草稿；
- 自动启用相似问法；
- 修改平台开关；
- 启动 Local Agent；
- 打开真实平台页面；
- 创建真实发送任务。

测试结果只能用于人工评估。运营人员确认效果后，再回到知识库或相似问法库完成修改、启用或发布。

## 15. 验收测试

### 15.1 拟人化

- 单问题回复不重复用户原问题；
- 评论默认不超过 1～2 句；
- 私信默认不超过 1～3 句；
- 同一会话不会重复问候；
- 不出现“综上所述”等典型 AI 句式；
- 时间、地址、费用、条件与知识库完全一致；
- 标准话术失败时能安全回退。

### 15.2 上下文抗干扰

测试：

```text
用户：社区活动怎么报名？
用户：那收费吗？
```

应理解为活动收费。

测试：

```text
用户：社区活动怎么报名？
用户：我想问一下，视频可以转载吗？
```

必须切换到视频转载，不得沿用活动主题。

测试：

```text
用户：亲子活动什么时候开始？
用户：志愿者活动怎么报名？
用户：那个收费吗？
```

存在歧义时必须询问具体活动，不能猜。

### 15.3 多用户隔离

至少模拟 100 个并发用户，包含：

- 20 个相同昵称；
- 多人发送相同问题；
- 不同平台同名用户；
- 同用户不同帖子评论；
- 用户生成期间继续发消息；
- AI 返回顺序与消息到达顺序不同；
- 页面私信列表重新排序；
- 视频号会话 ID 缺失；
- 私信和打招呼同名用户。

验收要求：

```text
跨会话上下文引用：0
跨用户错误发送：0
旧任务覆盖新任务：0
重复发送：0
目标不唯一仍自动发送：0
```

### 15.4 视频号身份

- 有 `conversationKey` 时可稳定定位；
- 无 `conversationKey` 时不使用长期上下文；
- 同名用户存在多个候选时停止自动发送；
- 通知包含昵称、入口、消息时间和最近消息；
- 当前未实现头像时，页面不得错误显示“已通过头像确认”；
- 后续实现头像后，头像只能作为组合证据。

### 15.5 小智即时测试

- 左侧导航名称显示为“小智”；
- 点击发送后立即发起服务端请求，不创建轮询任务；
- 不要求五平台开关开启；
- 不要求 Local Agent 在线；
- 不打开任何真实平台页面；
- 标准问题和相似问法精确命中目标在 1 秒内显示；
- AI语义路径不叠加平台轮询等待；
- 小智与五平台使用同一回复核心；
- 可选择正式知识库或当前上传批次草稿预览；
- 平台知识隔离、回复长度和评论/私信策略与真实平台一致；
- 连续追问可以验证上下文；
- 新建测试后旧上下文不再生效；
- 两名运营人员同时测试时会话不串；
- 测试消息不进入真实消息列表；
- 不创建真实回复任务、知识缺口工单或企微通知；
- 页面可查看命中知识、置信度、原因、处理结果和耗时；

## 16. 风险与降级策略

| 风险 | 处理方式 |
|---|---|
| Qwen 被旧上下文带偏 | 当前消息优先、双路匹配、话题切换检测 |
| Qwen 自然改写新增事实 | 事实锁定、审核话术、发送前校验 |
| 多用户上下文串台 | `conversation_id` 强制隔离、引用消息校验 |
| 用户生成期间继续发消息 | 会话版本变化后旧任务作废 |
| 视频号没有稳定用户 ID | 身份可信度分级、低可信禁用长期上下文 |
| 同名视频号用户 | 不按昵称合并；候选不唯一时停止发送 |
| 视频号头像无法采集 | 不依赖头像，使用稳定会话键或降级 |
| Agent 打开了错误聊天窗口 | 发送前重新核对入口、会话、昵称和最新消息 |
| AI 服务不可用 | 回退标准答案或进入技术异常，不自由生成 |
| 自然话术尚未审核 | 回退已发布标准答案 |
| 小智误触发真实平台流程 | 独立测试命名空间、独立接口、禁止创建发送任务 |
| 小智与真实平台回复不一致 | 共用同一 `reply-engine`，只替换输入和输出适配器 |
| 草稿测试污染正式知识 | 草稿仅绑定当前导入批次，正式平台继续只读已发布知识 |

## 17. 最终设计结论

本次优化不能只理解为“把提示词写得更像人”。正确方案是同时解决三件事：

### 1. 回复像真人

通过自然话术库、评论/私信风格、上下文承接、多问题自然编排和 AI 味检查实现。

### 2. 上下文不带偏

通过当前消息优先、只在省略时引用上下文、双路匹配、话题切换、歧义澄清实现。

### 3. 多用户不串台

通过稳定会话身份、数据库范围、每会话队列、版本失效、任务目标绑定和发送前页面核验实现。

昵称必须保留并用于转人工定位，但不能单独作为系统唯一身份。视频号当前没有正式头像识别能力，也没有稳定用户 ID 时，应优先寻找页面内部会话标识；仍无法确认时必须降级，不能为了自动回复率冒险合并或发送。

“小智”作为内部测试入口，应直接复用正式回复核心并通过 Web 请求即时返回，不经过五平台轮询、Local Agent 或 RPA。运营人员可以在知识发布前验证草稿批次，也可以用正式知识库模拟五个平台的评论或私信效果。

推荐实施顺序：

```text
会话隔离安全底座
→ 上下文意图解析
→ 拟人化回复与小智即时测试台
→ 自然话术库
→ 视频号身份增强
```

只有先完成会话安全底座，再加入上下文和拟人化，才能在多人真实咨询场景下同时保证自然、准确和不串台。
