# 智能回复拟人化、上下文理解与多用户会话隔离优化设计方案 V1.0

- 编写日期：2026-08-20
- 适用项目：天河 AI 数字员工平台（AI数字运营2）
- 项目目录：`D:\code\AI数字运营2`
- 当前状态：设计方案，尚未据此执行数据库迁移和回复链路改造
- 关联方案：`docs/知识库语义匹配与AI相似问法生成设计方案-V1.5.md`
- 本次范围：回复拟人化、连续上下文、话题切换、多用户并发隔离、视频号私信身份识别、转人工定位

---

## 1. 文档目的

当前平台已经可以完成知识库召回、Qwen 语义匹配、受知识约束的回复生成、问候引导、多问题拆分、知识缺口提示和用户主动转人工等流程。但实际聊天中仍存在以下体验和安全问题：

1. 回复过于书面、固定，容易让用户感觉是 AI 或模板机器人；
2. 当前单问题生成只看到本条消息和一条知识，不能自然承接“那收费吗”“地址呢”等追问；
3. 如果直接加入整段历史上下文，Qwen 可能受到旧话题干扰；
4. 用户突然切换话题时，系统必须以当前消息为准，不能继续沿用旧主题；
5. 多个用户同时咨询时，必须保证上下文、知识匹配、回复任务和实际发送目标互不串台；
6. 视频号私信页面当前未稳定取得用户 ID，也没有正式采集头像，不能把昵称当作唯一身份；
7. 转人工时必须保留昵称、消息入口、时间和原消息，让人工能够准确找到对应用户。

本方案将上述问题整合为一套完整的运行架构，目标是：

> 知识库负责保证“说什么是对的”，Qwen 负责理解“用户现在想问什么”和“怎样表达更自然”，系统负责保证“这条回复属于哪个用户、发到哪个会话”。

## 2. 当前实现核对结果

本节只描述当前源码已经存在的真实能力，不把建议方案写成已实现功能。

### 2.1 当前知识回复生成

当前 `src/services/qwen.js` 的 `composeReply()`：

1. 只向 Qwen 提供当前用户消息、唯一命中知识的问题和答案；
2. `temperature` 当前为 `0.1`；
3. 提示词要求知识库标准答案逐字、完整出现在回复中；
4. 不提供最近聊天上下文；
5. 不区分评论区和私信的自然表达风格。

`src/services/decision.js` 的 `validateReply()` 还会检查生成内容是否完整包含标准答案。因此现有回复安全性较高，但知识答案如果较正式，最终回复也会显得正式和机械。

### 2.2 当前多问题和固定话术

`src/services/conversation-intent.js` 当前已经支持：

- 纯问候检测；
- 显式“转人工”命令判断；
- 多问题拆分；
- 知识缺口话术；
- 多问题固定拼接。

当前多问题主要使用：

```text
关于你提出的问题：

1. 标准答案

2. 标准答案
```

问候、转人工、无法确认也主要是单套固定话术，因此重复使用时容易出现明显模板感。

### 2.3 当前会话区分方式

`src/server.js` 的 `messageConversationKey()` 当前会组合：

- 平台代码；
- 运营账号 ID；
- 消息类型；
- `conversationId`、`chatId`、`sessionId`、`userId`、`senderId` 等可用字段；
- 如果均不存在，可能退化使用 `user_name`；
- 最后可能退化为 `unknown`。

方向是正确的，但昵称和 `unknown` 不能作为多人长期上下文的可靠身份依据。

### 2.4 当前转人工通知

`src/services/manual-notification.js` 当前已经在通知标题和正文中带上用户昵称，例如：

```text
【视频号·私信】张先生需要转人工
用户名称：张先生
消息来源：私信
私信内容：“……”
```

因此本方案不会删除昵称。后续只是在昵称之外增加更可靠的系统会话身份和人工定位信息。

### 2.5 当前视频号私信采集

当前视频号代码已经：

- 区分“私信”和“打招呼消息”；
- 识别可见未读红点；
- 采集昵称、消息预览、消息时间；
- 尝试从 DOM 中读取 `data-conversation-id`、`data-session-id`、`data-chat-id`、`data-id`、`id` 等内部会话标识；
- 将可用标识保存到 `context.conversationKey`。

当前尚未正式实现：

- 视频号私信用户头像采集；
- `avatarUrl`；
- `avatarHash`；
- 稳定的视频号用户 ID；
- 无会话 ID 时的长期可靠身份合并。

因此，头像只能作为后续增强方向，不能作为当前已经可用的身份依据。

## 3. 设计目标与非目标

### 3.1 核心目标

1. 单问题回复更像真实社区运营人员，简短、自然、友好；
2. 不因拟人化而新增、改错时间、费用、地址、政策、条件或承诺；
3. 只有当前消息信息不完整时才使用上下文；
4. 当前消息包含完整新问题时，旧上下文不能覆盖当前意图；
5. 对话存在歧义时主动确认，不强行猜测；
6. 同一用户消息串行处理，不同用户可以并行处理；
7. Qwen 只能生成文字和意图判断，不能决定回复发给谁；
8. 昵称始终记录、展示，并在转人工通知中保留；
9. 视频号没有稳定用户 ID 时，按身份可信度分级处理；
10. 生成回复期间如果用户又发新消息，旧回复必须失效或重新合并；
11. 身份不足、目标不唯一、页面核验失败时禁止自动发送；
12. 所有改造必须保留现有知识库平台隔离和风险门禁。

### 3.2 非目标

第一阶段暂不做：

- 不让 Qwen 自由脱离知识库回答；
- 不直接把温度提高到高随机值；
- 不依靠随机添加“亲、哈、哦、表情”冒充拟人化；
- 不用昵称单独作为长期唯一用户 ID；
- 不把视频号私信和打招呼消息仅凭同名自动合并；
- 不在身份为低可信时使用长期上下文；
- 不一次性将全部历史聊天发送给 Qwen；
- 不自动触发真实平台测试消息或真实回复。

## 4. 总体架构

建议将回复链路拆为七层：

```text
平台消息采集
    ↓
会话身份与消息归属层
    ↓
短时消息聚合与会话版本层
    ↓
当前问题/上下文意图解析层
    ↓
知识召回与事实锁定层
    ↓
自然话术选择与拟人化编排层
    ↓
发送前会话、目标和页面核验层
```

每一层只做自己的职责：

- 身份层不能生成答案；
- Qwen 不能选择发送目标；
- 上下文只负责补全问题，不负责提供事实；
- 知识库只决定可使用的事实；
- 拟人化层只能改变表达，不得改变事实；
- Agent 只能向服务端已经绑定的目标会话发送。

## 5. 回复拟人化设计

### 5.1 当前“AI味”的主要来源

1. 标准答案必须原文完整包含；
2. 多问题固定使用编号模板；
3. 问候、转人工、知识缺口只有单套话术；
4. 不区分评论和私信口吻；
5. 不知道前面已经问候或回答过什么；
6. 知识库标准答案本身偏公告和书面表达；
7. 生成温度低，句式变化很少。

### 5.2 事实层与表达层分离

建议一条知识同时维护：

```text
标准问题
标准答案
必须保留事实
允许改写内容
自然回复话术
```

示例：

```text
标准问题：参加社区活动需要收费吗？

必须保留事实：
1. 是否收费以具体活动公告为准；
2. 公告未明确收费时不要先转账；
3. 可以私信工作人员确认。
```

允许生成的自然回复：

```text
这个要看具体活动公告哈。公告没写收费的话先别急着转账，可以先私信我们确认一下。
```

禁止生成：

```text
活动都是免费的。
```

### 5.3 自然回复话术库

建议新增每条知识的审核话术，例如：

- 稳妥版；
- 自然亲切版；
- 简洁版；
- 评论区版；
- 私信版；
- 简体版；
- 繁体版。

Qwen 在知识保存或运营人员点击生成时，生成 5～8 条候选话术。运营人员可以：

- 勾选启用；
- 手工修改；
- 设置默认话术；
- 标记评论或私信适用；
- 禁用不满意话术；
- 重新生成。

运行时优先使用已经审核启用的话术。没有启用话术时回退到标准答案，不能因为拟人化任务失败而影响知识回复可用性。

### 5.4 评论和私信差异

评论区：

- 默认 1～2 句；
- 直接回答；
- 尽量不重复用户问题；
- 不每次都加问候和结尾；
- 严格遵守平台长度限制。

私信：

- 可以 1～3 句；
- 允许自然承接上文；
- 可以引导用户补充活动名称等必要信息；
- 同一会话不重复问候；
- 不每条都说“如果还有问题欢迎咨询”。

### 5.5 多问题自然编排

两个简短问题优先自然合并，不强制编号：

```text
收费情况要看具体活动公告，公告没写收费的话先别转账。至于能不能带孩子，我这边暂时确认不了，需要人工确认的话请输入“转人工”。
```

三个以上、答案较长或条件较多时才分点：

```text
关于你提到的几个问题：

1. ……
2. ……
3. ……
```

保留用户已经确认的要求：多问题开头不重复原问题，使用“关于你提出的问题”或更自然的等价表达。

### 5.6 AI味发送前检查

增加语言检查器，检查：

- “根据您提供的信息”；
- “综上所述”；
- “希望以上回答对您有所帮助”；
- 重复问候；
- 重复用户原问题；
- 无意义固定结尾；
- 简单问题回复过长；
- 模板堆叠；
- 新增知识库中不存在的事实。

语言检查只能调整表达，不能改动事实锁定字段。

## 6. 上下文理解与抗干扰设计

### 6.1 核心原则

```text
当前消息优先；
上下文只补全省略信息；
上下文不能推翻当前消息；
上下文不能充当知识事实；
存在歧义时先询问确认。
```

### 6.2 当前消息独立判断

完整问题示例：

```text
我想问一下，你们的视频可以转载吗？
支付宝怎么转账？
怎么联系社区工作人员？
```

这些问题当前句已经包含明确对象和意图，应直接作为新问题处理，旧活动上下文不能覆盖。

依赖上下文的短句示例：

```text
那收费吗？
地址呢？
什么时候开始？
孩子可以吗？
这个怎么取消？
还要准备什么？
```

只有这类信息不完整的消息，才允许读取最近相关上下文。

### 6.3 话题切换与纠正信号

以下表达优先判定为话题切换或用户纠正：

```text
不是这个
我不是问报名
我说的是
换个问题
另外问一下
先不说这个
我想问的是
```

当前问题完整且与旧主题语义距离较大时，也应自动切换话题。

### 6.4 最小上下文窗口

不发送整个历史记录，只提供：

- 最近 2～4 轮同一会话消息；
- 最近已回答问题；
- 当前活动主题；
- 尚未解决问题；
- 必要的引用消息 ID。

超过设定时间、已经明确切换话题或主题已结束时，不继续继承旧上下文。

建议初始有效期：

- 5 分钟内：强关联候选；
- 5～30 分钟：结合内容判断；
- 超过 30 分钟：默认不直接继承，需要当前消息自己说明或询问确认。

时间只是辅助，最终仍以内容和会话状态为准。

### 6.5 两阶段 AI

第一阶段只做意图解析，输出严格 JSON，不直接生成答案：

```json
{
  "currentMessageComplete": false,
  "needsContext": true,
  "topicSwitched": false,
  "resolvedQuestion": "社区志愿者活动是否收费",
  "referencedMessageIds": [205, 206, 208],
  "subQuestions": ["社区志愿者活动是否收费"],
  "confidence": 0.94,
  "reason": "用户使用‘那’承接上一轮志愿者活动"
}
```

第二阶段在知识已经命中、事实已经锁定之后，才组织自然回复。

### 6.6 双路匹配

每条问题同时比较：

1. 当前消息独立匹配结果；
2. 上下文补全后的匹配结果。

选择规则：

- 当前消息独立匹配置信度高：优先当前消息；
- 当前消息不完整、补全后置信度明显提高：允许使用上下文；
- 两路都高但命中不同知识：询问用户确认；
- 两路都低：进入知识缺口，不强行猜测。

### 6.7 上下文置信度

建议：

- `>= 0.85`：可自动继承并回答；
- `0.65～0.85`：只有唯一主题时允许，否则先澄清；
- `< 0.65`：不继承，不自动猜测。

阈值后续根据真实消息回放测试调整。

### 6.8 多问题逐题处理

用户消息：

```text
那这个收费吗？另外你们的视频可以转载吗？
```

必须拆成：

1. “那这个收费吗”——需要活动上下文；
2. “你们的视频可以转载吗”——当前问题完整，不继承活动上下文。

不能对整条消息统一套用一个旧主题。

## 7. 多用户并发会话隔离设计

### 7.1 Qwen 的边界

Qwen 每次只能看到系统本次发送的内容。跨用户串台通常不是模型主动看到其他用户，而是系统查询、任务绑定或页面发送目标发生错误。

因此隔离必须依靠：

```text
稳定会话键
+ 数据库范围限制
+ 每会话队列
+ 任务目标绑定
+ 发送前页面核验
```

不能只靠提示词写“不要混淆用户”。

### 7.2 会话唯一命名空间

私信优先使用：

```text
平台 + 运营账号 + 平台会话ID/对方用户ID
```

评论优先使用：

```text
平台 + 运营账号 + 帖子ID + 根评论ID + 发言者平台ID
```

同一个用户在不同帖子下评论时，评论上下文默认分开，避免把不同作品的问题混在一起。

### 7.3 昵称的正确用途

昵称必须保存，用于：

- Web 展示；
- 人工通知；
- 搜索和人工定位；
- 页面发送前辅助核验。

昵称不能单独用于：

- 长期唯一会话 ID；
- 同名用户自动合并；
- 跨私信入口合并；
- 决定回复发送目标。

### 7.4 每会话串行、跨会话并行

```text
用户甲：甲1 → 甲2 → 甲3
用户乙：乙1 → 乙2
用户丙：丙1 → 丙2
```

甲、乙、丙可以同时处理，但同一会话内部必须按顺序处理。实现方式可采用：

- `conversation_id` 分区队列；
- 每会话互斥锁；
- 每会话版本号；
- 任务租约和超时回收。

### 7.5 上下文查询强制范围

只允许：

```sql
SELECT *
FROM messages
WHERE conversation_id = ?
ORDER BY sequence_no DESC
LIMIT ?;
```

禁止使用全局“最近消息”作为上下文：

```sql
SELECT *
FROM messages
ORDER BY created_at DESC
LIMIT ?;
```

### 7.6 回复任务绑定

每个任务至少绑定：

```json
{
  "replyJobId": 9001,
  "messageId": 208,
  "conversationId": 35,
  "conversationVersion": 16,
  "platformCode": "wechat_channels",
  "accountId": 3,
  "targetPlatformUserId": null,
  "targetConversationKey": "abc123",
  "targetDisplayName": "张先生",
  "inboxType": "GREETING"
}
```

Qwen 无权修改这些目标字段，只能返回回复文字、意图和引用消息 ID。

### 7.7 生成期间新消息处理

生成开始时记录：

```text
conversationVersion=16
latestMessageId=208
```

发送前重新检查。如果同一会话已经变成版本 17 或最新消息 209：

1. 旧回复任务标记为 `STALE`；
2. 不发送旧结果；
3. 合并新消息后重新拆分、匹配和生成；
4. 不能把最新消息标记为已读或已处理却没有回答。

其他用户的新消息不影响本会话任务。

### 7.8 发送前目标核验

Agent 在真实页面发送前必须核对：

- 平台；
- 当前运营账号；
- 私信/打招呼入口；
- 会话内部标识；
- 昵称；
- 当前最新用户消息；
- 任务绑定的原消息；
- 页面是否存在多个同名候选。

目标不唯一或任一关键字段冲突时，停止发送并返回 `TARGET_IDENTITY_UNCERTAIN`。

## 8. 视频号无稳定用户 ID 的身份方案

### 8.1 事实边界

当前系统能采集昵称、消息预览、时间、未读状态、入口类型，并尝试读取 DOM 内部 `conversationKey`。当前没有正式头像采集，也没有稳定视频号用户 ID。

### 8.2 身份分级

#### HIGH：高可信

满足任一：

- 页面内部稳定 `conversationKey`；
- 网络请求或组件数据中的稳定联系人/会话 ID；
- 可跨刷新、跨排序重新定位的稳定线程键。

允许：

- 长期上下文；
- 自动连续回复；
- 重启后继续识别；
- 私信发送前按稳定键定位。

#### MEDIUM：中可信

在后续实现头像采集后，可使用：

```text
运营账号 + 消息入口 + 昵称 + 头像哈希
```

允许：

- 短期上下文；
- 发送前严格核验；
- 不自动跨入口合并；
- 不在存在多个候选时自动发送。

#### LOW：低可信

只有：

- 昵称；
- 最新消息；
- 时间；
- 私信/打招呼入口。

只允许：

- 记录和展示消息；
- 生成转人工通知；
- 当前页面保持不变且目标唯一时进行受限单轮处理；
- 不使用长期历史上下文；
- 不将同名用户合并；
- 页面重新排序、重启或目标不唯一时禁止自动发送。

### 8.3 头像后续采集

头像是增强信号，不是当前能力。后续需要新增：

- `avatar_url`；
- `avatar_hash`；
- 头像采集来源；
- 头像最后更新时间；
- 头像是否可稳定重取。

头像也不能单独作为绝对用户 ID，因为用户可能更换头像；应与昵称、入口和其他会话证据组合使用。

### 8.4 私信与打招呼消息合并

只有稳定会话标识一致时才自动合并。若只有相同昵称，不自动合并，分别显示：

```text
张先生｜私信
张先生｜打招呼消息
```

转人工通知必须明确写明入口。

## 11. AI 接口设计

### 11.1 意图解析接口

输入仅包含同一会话经过筛选的最近消息和当前消息。输出严格 JSON：

```json
{
  "conversationId": 35,
  "currentMessageId": 208,
  "currentMessageComplete": false,
  "needsContext": true,
  "topicSwitched": false,
  "resolvedQuestion": "社区活动是否收费",
  "referencedMessageIds": [205, 206, 208],
  "subQuestions": [
    {
      "text": "社区活动是否收费",
      "needsContext": true
    }
  ],
  "confidence": 0.94
}
```

服务端验证引用消息必须全部属于同一 `conversation_id`，否则结果作废。

### 11.2 自然回复接口

输入：

- 当前用户表达；
- 消息类型；
- 最近必要上下文；
- 已锁定知识；
- 必须保留事实；
- 已审核话术；
- 平台长度限制；
- 语言脚本：简体或繁体；
- 当前会话是否已问候。

输出：

```json
{
  "replyText": "这个要看具体活动公告哈。公告没写收费的话先别急着转账，可以先私信我们确认一下。",
  "usedKnowledgeIds": [12],
  "usedVariantIds": [88],
  "addedFacts": [],
  "style": "NATURAL_FRIENDLY",
  "confidence": 0.96
}
```

服务端不能只相信 `addedFacts`，还需要基于必须保留字段、禁用表达和风险规则做独立校验。

## 15. 验收测试

### 15.1 拟人化

- 单问题回复不重复用户原问题；
- 评论默认不超过 1～2 句；
- 私信默认不超过 1～3 句；
- 同一会话不会重复问候；
- 不出现“综上所述”等典型 AI 句式；
- 时间、地址、费用、条件与知识库完全一致；
- 标准话术失败时能安全回退。

### 15.2 上下文抗干扰

测试：

```text
用户：社区活动怎么报名？
用户：那收费吗？
```

应理解为活动收费。

测试：

```text
用户：社区活动怎么报名？
用户：我想问一下，视频可以转载吗？
```

必须切换到视频转载，不得沿用活动主题。

测试：

```text
用户：亲子活动什么时候开始？
用户：志愿者活动怎么报名？
用户：那个收费吗？
```

存在歧义时必须询问具体活动，不能猜。

### 15.3 多用户隔离

至少模拟 100 个并发用户，包含：

- 20 个相同昵称；
- 多人发送相同问题；
- 不同平台同名用户；
- 同用户不同帖子评论；
- 用户生成期间继续发消息；
- AI 返回顺序与消息到达顺序不同；
- 页面私信列表重新排序；
- 视频号会话 ID 缺失；
- 私信和打招呼同名用户。

验收要求：

```text
跨会话上下文引用：0
跨用户错误发送：0
旧任务覆盖新任务：0
重复发送：0
目标不唯一仍自动发送：0
```

### 15.4 视频号身份

- 有 `conversationKey` 时可稳定定位；
- 无 `conversationKey` 时不使用长期上下文；
- 同名用户存在多个候选时停止自动发送；
- 通知包含昵称、入口、消息时间和最近消息；
- 当前未实现头像时，页面不得错误显示“已通过头像确认”；
- 后续实现头像后，头像只能作为组合证据。

## 16. 风险与降级策略

| 风险 | 处理方式 |
|---|---|
| Qwen 被旧上下文带偏 | 当前消息优先、双路匹配、话题切换检测 |
| Qwen 自然改写新增事实 | 事实锁定、审核话术、发送前校验 |
| 多用户上下文串台 | `conversation_id` 强制隔离、引用消息校验 |
| 用户生成期间继续发消息 | 会话版本变化后旧任务作废 |
| 视频号没有稳定用户 ID | 身份可信度分级、低可信禁用长期上下文 |
| 同名视频号用户 | 不按昵称合并；候选不唯一时停止发送 |
| 视频号头像无法采集 | 不依赖头像，使用稳定会话键或降级 |
| Agent 打开了错误聊天窗口 | 发送前重新核对入口、会话、昵称和最新消息 |
| AI 服务不可用 | 回退标准答案或进入技术异常，不自由生成 |
| 自然话术尚未审核 | 回退已发布标准答案 |

## 17. 最终设计结论

本次优化不能只理解为“把提示词写得更像人”。正确方案是同时解决三件事：

### 1. 回复像真人

通过自然话术库、评论/私信风格、上下文承接、多问题自然编排和 AI 味检查实现。

### 2. 上下文不带偏

通过当前消息优先、只在省略时引用上下文、双路匹配、话题切换、歧义澄清实现。

### 3. 多用户不串台

通过稳定会话身份、数据库范围、每会话队列、版本失效、任务目标绑定和发送前页面核验实现。

昵称必须保留并用于转人工定位，但不能单独作为系统唯一身份。视频号当前没有正式头像识别能力，也没有稳定用户 ID 时，应优先寻找页面内部会话标识；仍无法确认时必须降级，不能为了自动回复率冒险合并或发送。

推荐实施顺序：

```text
会话隔离安全底座
→ 上下文意图解析
→ 拟人化回复
→ 自然话术库
→ 视频号身份增强
```

只有先完成会话安全底座，再加入上下文和拟人化，才能在多人真实咨询场景下同时保证自然、准确和不串台。
