# AI CONTENT ENGINE 语音识别 422 修复

## 原因

天河运行配置为 `https://api.deepseek.com`、`deepseek-flash`，音视频转文字模型仍保存为 `qwen3-asr-flash`。原实现将统一 Base URL 和 Key 同时用于文案与语音识别，导致千问的 `input_audio` 请求发到不支持该类型的 DeepSeek 接口，返回 HTTP 422。

此前 OpenChatCut 的本地识别只在编辑器浏览器中运行，未覆盖天河“AI CONTENT ENGINE”的服务端文案生成链路。

恢复识别后的真实测试还发现，文案与知识生成沿用千问的 `enable_thinking: false`，DeepSeek 未识别该参数，推理占满输出额度后没有返回完整文案。已为 DeepSeek 接口改用 `thinking: { type: 'disabled' }`；千问请求保留原有参数。

## 修复

- 在天河 Web 镜像编译安装固定版本 whisper.cpp v1.9.2，校验源代码压缩包 SHA-256；不依赖宿主机手工安装。
- 通过只读挂载复用 OpenChatCut 已下载的 `ggml-small-q5_1.bin`，不需要新增语音 API Key，也不向 DeepSeek 上传音频。
- AI 设置中的音视频转文字模型设为 `local:whisper-small`，文案提炼、润色及知识草稿继续使用天河统一模型和 Key。
- 本地请求使用独立临时目录，识别成功或失败后均清理；组件缺失、模型缺失、超时及空结果均返回明确错误。
- 保留千问在线识别兼容逻辑；误配到 DeepSeek 时，在发送音频前返回可操作的配置提示。
- 本部署的识别超时为 180 秒，总处理预算为 290 秒，主程序代理同步延长等待，避免本地处理被原来的 120 秒代理超时截断。

## 重新部署

```powershell
docker compose -f compose.yaml -f compose.wechat.yaml -f compose.workbench.yaml build --build-arg HTTP_PROXY= --build-arg HTTPS_PROXY= web
docker compose -f compose.yaml -f compose.wechat.yaml -f compose.workbench.yaml up -d --no-deps --wait web
docker exec tianhe-dev-web-1 node scripts/setup-material-local-asr.mjs
```

配置脚本先校验模型和识别程序，备份原 ASR 设置后再修改数据库配置；原配置备份在 Web 数据卷 `backups/local-asr/`。Compose 环境变量提供默认值，数据库中保存的设置优先，因此首次修复必须运行该脚本。

新机器需先按 `素材智剪帧预览与双语字幕-20261026.md` 安装 Whisper Small。设置页面“专用模型 → 音视频转文字模型”可查看当前值。失败任务不会自动重跑，刷新页面后重新生成即可。
