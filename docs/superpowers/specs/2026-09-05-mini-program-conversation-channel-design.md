# 小程序文字对话接入设计方案 V1.0

- 编写日期：2026-09-05
- 适用项目：天河 AI 数字员工运营平台
- 设计状态：已确认，尚未实施
- 接入方式：在现有 Web 后端增加隔离的开放接口

## 1. 目标

把小程序作为新的文字私信渠道接入现有系统，复用已有的安全路由、正式 RAG、上下文澄清和企业微信转人工能力，同时使用服务端回调把 AI 回复交给小程序服务器。

本期必须实现：

1. 小程序服务器通过签名接口提交用户文字消息。
2. 新用户的正常咨询进入现有安全判断与正式 RAG 链路。
3. AI 回复通过可靠回调队列发送给小程序服务器。
4. 风险消息、明确的转人工请求、RAG 故障和后台人工操作可触发企微通知。
5. 企微确认通知成功后，当前会话停止采集和回复。
6. 曾经转过人工的用户开启新会话时，跳过 RAG，直接再次通知人工。
7. 后台增加“小程序对话”页面，只用于查看状态和发起转人工，不承载人工回复。

## 2. 非目标

本期不实现：

- 图片、语音、视频、文件或富文本消息；
- 在本后台输入和发送人工回复；
- 采集小程序客服人员的回复；
- 等待小程序返回人工认领、处理完成或会话结束状态；
- 把小程序加入 Local Agent、浏览器 RPA、内容发布或平台登录流程；
- 对公网开放管理后台、内部 `/api/*` 或 RAG 服务；
- 多个小程序应用的后台自助配置。V1 只接入一个由环境变量配置的 `appId`。

## 3. 已确认的关键规则

### 3.1 会话和用户身份

- `appId + conversationId` 唯一标识一次咨询会话。
- `appId + messageId` 唯一标识一条外部消息。
- `appId + userId` 唯一标识一个小程序用户，并用于记录是否曾经成功转人工。
- 一个 `appId + conversationId` 在首次创建时绑定唯一 `userId`；后续请求携带不同用户 ID 时拒绝处理，防止串会话。
- 对方小程序必须在用户开启一次新的咨询时生成新的 `conversationId`。重复使用已经终止的 `conversationId` 会被当作原会话的后续消息忽略。

### 3.2 转人工后的行为

- 触发转人工后，会话立即进入 `HANDOFF_PENDING`，禁止继续查询 RAG 或生成、发送 AI 回复。
- `HANDOFF_PENDING` 期间到达的新文字继续保存到当前会话，便于排查企微通知延迟期间发生的消息；它们不进入 RAG，也不额外创建企微通知。最初的通知记录继续重试。
- 只有企业微信接口明确返回成功后，才把会话视为转人工完成。
- 转人工完成后，同一个 `conversationId` 的新消息只完成鉴权和接收确认，不创建消息记录、不保存正文、不回复，也不重复通知企微。
- 技术日志只能记录请求编号、结果码和耗时，不能记录被忽略消息的正文。
- 转人工成功后，不向小程序自动发送“已转人工”提示。

### 3.3 历史人工用户

- 只有企微通知明确成功，才把 `appId + userId` 标记为历史人工用户。
- 历史人工用户使用新的 `conversationId` 再次发言时，系统保存该新会话的第一条文字，用作企微通知依据。
- 该新会话从创建时就进入 `HANDOFF_PENDING`，不经过安全问答、RAG 或自动回复。
- 企微通知中明确标注“历史人工用户再次咨询”，并包含用户 ID、新会话 ID、首条文字和收到时间。
- 通知成功后，新会话同样终止采集和回复。

## 4. 总体架构

```text
小程序前端
  -> 小程序服务器
  -> 公网反向代理（只放行指定开放接口）
  -> 本地 Web 后端开放接口
  -> SQLite 持久化消息与处理任务
  -> 安全路由 / 正式 RAG / 会话澄清
  -> 小程序回调 Outbox -> 小程序服务器 -> 小程序前端
  -> 企业微信通知 Outbox -> 人工客服
```

小程序属于服务端消息渠道，而不是浏览器平台。它使用现有 `messages`、`conversations` 和知识问答规则，但采用独立的输入鉴权和回复传输层。

在 `platforms` 和 `accounts` 中创建 `mini_program` 对应记录，以满足现有消息和会话外键。它不得加入五平台的运行时允许列表、Local Agent 注册表、浏览器控制、平台启停和发布目标列表。

## 5. 模块边界

实现时将小程序职责从当前较大的 `src/server.js` 中分离为可独立测试的服务：

### 5.1 开放接口鉴权

负责请求体大小、字段格式、时间窗口、Nonce、防重放和 HMAC 校验。该模块只返回规范化请求或稳定错误，不处理业务消息。

### 5.2 小程序接入服务

负责解析应用、用户和会话，执行消息幂等判断，识别终止会话及历史人工用户，并在事务中写入消息和持久化处理任务。

### 5.3 共享消息处理器

从现有消息处理流程提取清晰入口，让 RPA 采集消息与小程序消息复用安全路由、RAG、澄清和转人工决策。输出回复意图或转人工意图，不决定具体发送方式。

### 5.4 回复分发器

根据渠道选择传输方式：

- 五个平台继续创建 Local Agent `REPLY` 任务；
- `mini_program` 只创建小程序回调 Outbox 记录；
- 小程序消息永远不会创建 Local Agent 或浏览器 RPA 任务。

### 5.5 小程序回调 Outbox Worker

负责按会话顺序发送回调、校验会话仍允许机器人回复、处理超时与重试，并保存真实送达结果。

### 5.6 小程序后台查询服务

只提供会话列表、对话详情、状态汇总、转人工和重试操作。它不包含人工回复接口。

## 6. 开放接口合同

### 6.1 接收消息

```http
POST /open-api/v1/mini-program/messages
Content-Type: application/json
X-Mini-App-Id: <appId>
X-Timestamp: <Unix 秒>
X-Nonce: <随机字符串>
X-Signature: <小写十六进制 HMAC-SHA256>
```

请求体：

```json
{
  "appId": "configured-app-id",
  "conversationId": "consultation-20260905-001",
  "messageId": "message-001",
  "userId": "user-001",
  "text": "请问这项业务怎么办理？",
  "sentAt": "2026-09-05T09:30:00.000Z"
}
```

字段规则：

- 六个字段全部必填，且必须是字符串。
- `appId` 必须同时匹配请求头和本机配置。
- `conversationId`、`messageId`、`userId` 去除首尾空白后长度为 1 至 128 个字符。
- `text` 去除首尾空白后长度为 1 至 2000 个 Unicode 字符。
- `sentAt` 必须是可解析的 ISO 8601 时间。
- 请求体最大 32 KiB；出现附件字段或非文字消息类型时返回参数错误。

新消息在事务中持久化后立即返回 `202`，RAG、企微通知和回复回调由后台 Worker 完成：

```json
{
  "ok": true,
  "accepted": true,
  "messageId": "message-001",
  "status": "ACCEPTED"
}
```

重复的 `appId + messageId` 仍返回 `202` 和最初的 `ACCEPTED` 结果，不重复保存、处理、回复或通知。终止会话的后续消息也返回 `202`，但响应状态为 `IGNORED_HANDOFF_COMPLETED`，且不保存正文。

通过鉴权和参数校验后的判断顺序固定为：先按 `appId + messageId` 返回历史幂等结果，再校验已有会话绑定的 `userId`，然后判断会话是否终止，最后才创建新消息。这样，响应丢失后的原消息重试仍得到原结果，而错误复用其他用户会话 ID 的请求不会被静默忽略。

### 6.2 签名算法

双方共享一个只通过环境变量配置的密钥。签名原文固定为：

```text
HTTP_METHOD + "\n" +
REQUEST_PATH + "\n" +
X_TIMESTAMP + "\n" +
X_NONCE + "\n" +
SHA256_HEX(RAW_REQUEST_BODY)
```

`X-Signature` 为上述原文的 `HMAC-SHA256` 小写十六进制结果。服务端使用常量时间比较，并执行以下防重放规则：

- 时间戳与服务器时间相差不得超过 300 秒；
- `appId + nonce` 在 10 分钟内不得重复；
- 已使用的 Nonce 持久化到 SQLite，服务重启后仍然有效；
- 过期 Nonce 由定时清理任务删除。

签名必须基于实际发送的原始请求字节，不能在接收端重新序列化 JSON 后再计算。调用方因超时重试同一个 `messageId` 时，必须生成新的时间戳、Nonce 和签名；业务幂等仍由 `appId + messageId` 保证。

### 6.3 AI 回复回调

回调地址是本机配置的固定 URL，不能由入站请求指定，避免 SSRF。生产环境必须使用 HTTPS；本地测试只允许回调到环回地址。

```json
{
  "eventId": "reply-event-uuid",
  "type": "assistant.message",
  "appId": "configured-app-id",
  "conversationId": "consultation-20260905-001",
  "userId": "user-001",
  "inReplyToMessageId": "message-001",
  "text": "办理时请携带有效身份证件。",
  "createdAt": "2026-09-05T09:30:02.000Z"
}
```

回调使用与入站接口相同的签名请求头和算法。任意 `2xx` 响应视为已接收，超时、网络错误、非 `2xx` 均进入重试。对方必须使用 `eventId` 幂等消费，保证本系统在响应丢失后重试时不会重复展示回复。

## 7. 数据设计

### 7.1 复用现有数据

- 平台代码：`mini_program`
- 消息类型：`PRIVATE_MESSAGE`
- 会话命名空间：`mini-program:{appId}:{conversationId}`
- `messages.external_id`：保存带应用命名空间的值，避免与其他平台或应用碰撞。
- 原始 `messageId`、`conversationId`、`userId`、`sentAt` 和传输类型保存在结构化上下文中。
- 正常消息继续使用现有 `messages`、`conversations`、消息事件和回复批次能力。

### 7.2 新增持久化数据

新增以下逻辑表，具体迁移遵循项目现有 SQLite 增量迁移方式：

1. `mini_program_users`
   - 唯一键：`account_id + external_user_id`
   - 保存首次和最近一次成功转人工时间、最近会话、成功转人工次数。
2. `mini_program_request_nonces`
   - 唯一键：`app_id + nonce`
   - 保存过期时间，仅用于防重放，不保存请求正文。
3. `mini_program_processing_jobs`
   - 唯一关联一个已保存的 `message_id`。
   - 保存 `PENDING`、`RUNNING`、`RETRY_WAIT`、`COMPLETED`、`FAILED` 状态、租约、尝试次数和错误摘要。
4. `mini_program_callback_outbox`
   - `event_id` 唯一，关联来源消息和会话。
   - 保存规范化回调载荷、状态、尝试次数、下次尝试时间、HTTP 状态、错误摘要和送达时间。

数据库不保存共享密钥。密钥、允许的 `appId`、回调 URL 和功能开关只来自环境变量，并在日志和 API 响应中脱敏。

## 8. 状态机

现有会话状态继续作为业务事实来源：

```text
BOT_ACTIVE
  -> HANDOFF_PENDING
  -> HUMAN_MANAGED（小程序页面显示为“已转人工，本地已终止”）
```

转换规则：

- 新普通用户会话从 `BOT_ACTIVE` 开始。
- 风险路由、明确转人工命令、RAG 故障、历史人工用户或后台“转人工”操作进入 `HANDOFF_PENDING`。
- 进入 `HANDOFF_PENDING` 的同一事务取消尚未发送的 AI 回复与回复批次。
- 企微通知明确成功后调用现有会话确认能力，进入 `HUMAN_MANAGED`，并在同一事务更新 `mini_program_users` 的历史人工标记。
- 企微通知失败时保持 `HANDOFF_PENDING`，禁止机器人恢复工作。
- `HANDOFF_PENDING` 期间的新消息可入库，但不产生新的处理任务、AI 回复或企微通知；原通知成功后，后续新消息才开始执行完全忽略规则。
- 小程序接入层把 `mini_program + HUMAN_MANAGED` 解释为终止状态，在任何消息入库之前短路。

同一会话的入站处理、转人工转换和回调发送必须串行化。回调 Worker 在真正发出 HTTP 请求前再次读取会话状态；只要会话已进入 `HANDOFF_PENDING` 或 `HUMAN_MANAGED`，尚未发送的回调立即取消。这样可以避免转人工与机器人回复并发竞争。

## 9. 消息处理流程

### 9.1 普通新用户

```text
鉴权和参数校验
-> 消息与处理任务事务落库
-> 返回 202
-> 安全路由
-> 问候直接回答，或查询正式 RAG
-> 生成回复
-> 回调 Outbox 落库
-> 按会话顺序回调小程序服务器
```

正式 RAG 只查询已发布知识，保持当前单一 RAG 体系，不复制或物理合并知识库。

无可靠答案时沿用私信语义：最多进行三轮澄清；达到上限时提示用户可发送“转人工”，但只有用户明确发送转人工指令、命中风险规则、RAG 不可用或后台操作时才真正通知企微。

### 9.2 当前会话转人工

```text
触发转人工
-> 原子切换 HANDOFF_PENDING
-> 取消待发送机器人回复
-> 可靠写入企微通知 Outbox
-> 企微明确成功
-> 切换 HUMAN_MANAGED
-> 标记用户为历史人工用户
-> 当前 conversationId 永久停止采集和回复
```

### 9.3 历史人工用户的新会话

```text
鉴权
-> 发现 conversationId 是新的
-> 发现 appId + userId 有成功转人工历史
-> 保存首条消息
-> 创建会话并直接切换 HANDOFF_PENDING
-> 企微通知“历史人工用户再次咨询”
-> 成功后终止该新会话
```

### 9.4 已终止会话的后续消息

```text
鉴权
-> 根据 appId + conversationId 命中 HUMAN_MANAGED
-> 返回 202 / IGNORED_HANDOFF_COMPLETED
-> 不创建消息、处理任务、回调或企微通知
```

## 10. 可靠性与恢复

- 入站接口只在消息和处理任务都成功提交后返回 `202`。
- SQLite 唯一键保证并发重复请求只产生一条消息和一个处理任务。
- Processing Worker 使用租约领取任务；进程退出后，过期租约可恢复为待处理。
- Processing Worker 对瞬时错误按 5 秒、30 秒和 2 分钟最多自动重试三次；仍失败时将会话转入 `HANDOFF_PENDING`，并通过企微通知“消息处理技术异常”，不得静默丢弃或猜测回复。
- 回调按同一会话串行发送，后一条不能越过前一条。
- 回调重试采用退避间隔：5 秒、30 秒、2 分钟、10 分钟、1 小时，之后每 6 小时一次，最多自动尝试 10 次。
- 达到自动重试上限后状态为 `FAILED`，记录留在 Outbox，后台可手动重新排队，不删除回复。
- 回调地址未配置时状态为 `NOT_CONFIGURED`，回复保留但不发起网络请求。
- 企微继续使用现有通知 Outbox；企微没有明确成功回执时绝不把会话标记为转人工完成。
- 服务启动时恢复过期的 Processing 和 Callback 租约，并继续处理到期任务。
- 日志不得输出共享密钥、完整签名、用户消息正文或完整回调载荷。

## 11. 管理后台页面

侧边栏顺序调整为：

```text
评论与私信
小程序对话
转人工记录
```

“小程序对话”页面包含：

1. 状态摘要：开放接口开关、回调配置、最近接收时间、待处理任务、待回调、企微通知失败数。
2. 会话列表：用户 ID、会话 ID、最后一条已保存文字、最后活动时间、是否历史人工用户、会话状态。
3. 对话详情：终止前的用户文字、AI 回复、知识命中、回复回调状态、企微通知状态及错误摘要。
4. 筛选：全部、AI 处理中、回复待发送、转人工通知中、已转人工、异常。
5. 操作：刷新、对 `BOT_ACTIVE` 会话发起转人工、重试失败的企微通知、重试失败的回复回调。

页面明确不提供人工回复输入框，不展示消息详细知识正文，不允许查看或修改共享密钥。按钮采用项目现有图标和样式，状态变化不改变列表和工具栏的稳定尺寸。

## 12. 管理接口

以下接口继续受现有后台登录鉴权保护，不对公网开放：

- `GET /api/mini-program/status`
- `GET /api/mini-program/conversations`
- `GET /api/mini-program/conversations/:id/messages`
- `POST /api/mini-program/conversations/:id/handoff`
- `POST /api/mini-program/notifications/:id/retry`
- `POST /api/mini-program/callbacks/:id/retry`

不存在人工回复接口。后台转人工接口必须具备幂等键；重复点击不会产生重复通知。

## 13. 错误处理

| 场景 | HTTP/状态 | 行为 |
|---|---|---|
| 签名错误、未知 appId、时间戳过期或 Nonce 重放 | `401` | 不写业务数据 |
| JSON、字段、长度、时间或文字类型错误 | `400` | 不写业务数据 |
| conversationId 已绑定其他 userId | `409 CONVERSATION_USER_MISMATCH` | 不保存、不处理 |
| 正常新消息 | `202 ACCEPTED` | 持久化后异步处理 |
| 重复 messageId | `202 ACCEPTED` | 返回最初结果，不重复处理 |
| 已终止 conversationId | `202 IGNORED_HANDOFF_COMPLETED` | 不保存正文、不回复、不通知 |
| SQLite 暂时不可写 | `503` | 不声称接收成功，由调用方重试 |
| RAG 不可用 | 业务转人工 | 禁止生成猜测答案 |
| 回调网络失败或非 2xx | `RETRY_WAIT` | 保留回复并退避重试 |
| 企微未配置或发送失败 | `HANDOFF_PENDING` | AI 保持禁用，通知继续重试 |

错误响应包含稳定的机器错误码和简短中文说明，不包含堆栈、数据库结构、密钥或签名细节。

## 14. 配置与公网边界

新增环境配置：

- `MINI_PROGRAM_API_ENABLED`
- `MINI_PROGRAM_APP_ID`
- `MINI_PROGRAM_SHARED_SECRET`
- `MINI_PROGRAM_CALLBACK_URL`
- `MINI_PROGRAM_CALLBACK_TIMEOUT_MS`

开放接口默认关闭。启用前必须存在合法的 `appId` 和共享密钥；缺少回调 URL 时允许接收和生成回复，但回复保持 `NOT_CONFIGURED`，后台必须明显告警。

公网反向代理只允许精确路径 `POST /open-api/v1/mini-program/messages`，并设置请求体、速率、连接数和超时限制。不得把 `127.0.0.1:3100` 整站、内部管理 API、静态后台页面或 `127.0.0.1:18080` 的 RAG 服务直接暴露到公网。

## 15. 测试方案

### 15.1 单元测试

- HMAC 规范化、常量时间校验、时间窗口和 Nonce 重放；
- 字段、Unicode 长度、空白文字和请求体限制；
- 用户历史判断和会话状态转换；
- 回调退避、状态映射和会话顺序；
- 终止会话短路且不保存正文；
- 小程序回复选择 Callback，而非 RPA。

### 15.2 集成测试

- 新用户问候、知识命中和正式 RAG 回答；
- 最多三轮澄清及明确转人工命令；
- 风险消息、RAG 故障和后台按钮转人工；
- 企微成功前保持 `HANDOFF_PENDING`，成功后终止；
- 历史人工用户使用新会话时直接通知人工；
- 并发重复消息、并发首消息和重复转人工不产生重复副作用；
- 回调 2xx、超时、非 2xx、响应丢失和手动重试；
- 服务重启后处理任务、回调任务和企微任务继续恢复；
- 全程没有为 `mini_program` 创建 `agent_jobs.job_type='REPLY'` 任务。

### 15.3 回归与界面测试

- 现有五个平台采集、RPA 回复、转人工和 RAG 测试继续通过；
- 小程序页面登录保护、筛选、详情、转人工和重试操作通过；
- 使用桌面和移动宽度截图检查文本溢出、按钮遮挡、空状态和长 ID；
- 通过浏览器网络记录确认页面不会获得共享密钥，也不会直接访问开放接口或 RAG。

## 16. 验收标准

满足以下全部条件才可视为完成：

1. 合法签名的文字消息能够稳定落库并快速返回，非法或重放请求被拒绝。
2. 相同消息无论重试或并发多少次，都只有一次业务处理和一次对外副作用。
3. 普通新用户可得到正式 RAG 回复，回复只经固定回调发送。
4. 企微未确认成功时不会错误显示“已转人工”，也不会恢复 AI。
5. 企微成功后，当前会话的后续正文不入库、不回复、不重复通知。
6. 历史人工用户的新会话保存首条文字并直接通知企微，通知内容明确标注历史身份。
7. 小程序消息不会创建或唤醒 Local Agent、浏览器或 RPA 回复任务。
8. 回调和通知失败可观察、可自动恢复、可人工重试，服务重启不丢任务。
9. 后台页面具备查看和转人工能力，但不存在后台人工回复路径。
10. 公网部署文档明确只映射开放消息接口，RAG 和管理后台保持本地边界。

## 17. 上线顺序

1. 完成数据库迁移、模块和自动化测试，功能开关保持关闭。
2. 本地配置测试 `appId`、密钥和模拟回调服务，完成签名、幂等、RAG、回调和企微全链路测试。
3. 使用真实企微验证“明确成功才终止”的状态转换。
4. 对方实现新的 `conversationId` 规则、回调验签和 `eventId` 幂等。
5. 配置受限公网反向代理，只放行开放消息接口。
6. 小范围启用并观察接收、处理、回调和企微队列。
7. 稳定后再正式启用；出现异常可关闭开放接口开关，已落库任务和记录保持可恢复。
