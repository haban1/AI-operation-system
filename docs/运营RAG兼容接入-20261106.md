# 运营 RAG：回答、回问与人设

这次在运营系统现有 `rag-service` 中接入 Traceable RAG 的核心策略。微信助手使用的
另一套 RAG 不受影响。运营的 API、知识上传/测试/发布/回滚、会话快照和平台发送链路
继续由本项目管理，没有将独立 RAG 的数据库或向量索引覆盖过来。

## 先理解三个决定

| 情况 | 处理 | 为什么 |
|---|---|---|
| 问题有明确主题，包括宽泛的入门或概览 | 检索，再判断证据 | 不要求用户先选课程、偏好或补无关资料 |
| “这个怎么办”等确实缺少对象，历史也不能补全 | 默认累计第五次仍未明确时转人工 | 需要的是用户意图 |
| 明确的问题检索两轮仍无可靠证据 | 私信说明资料不足，不累计澄清轮次 | 缺的是系统证据，反复问用户不能修复召回 |

私信的业务引导/澄清默认上限为 **5 次**：前四次可继续澄清，第五次仍未明确业务时
转人工，不再发送第五条重复回问。次数在本次待澄清周期内累计，插入问候不会增加或
清零；得到可靠知识答复后清零。证据不足不消耗次数，也不清除已累计的次数。
`BUSINESS_GUIDANCE_MAX_ATTEMPTS=5` 可按部署覆盖（支持 1–20）；已有环境若显式设为
3，升级时需将其改为 5 并重启主服务。对话历史仍只取最近三轮，与累计次数独立。

评论保持原有单轮规则：没有可靠知识仍转人工。主动要求人工、风险内容、已经人工接管
的会话、服务故障和无法满足平台长度限制的回答，继续按原有业务规则处理。
这次没有把所有人工处理都取消，也没有通过降低证据阈值提高表面回答率。

## 数据怎么走

```text
平台消息 / 小智测试
  → 原有风险、人工状态、会话隔离和业务路由
  → RAG：冻结已发布版本或已选测试版本
  → 原始问题 + 用户历史主语 → 搜索改写（不增加用户需求）
  → 向量召回 + BM25 → RRF 合并 → 全局 rerank Top 6
  → 单跳：动态 floor 后最多 4；多跳：全部保留最多 6
  → Gate 审核这批证据
      不足 → 最多 4 条第二轮查询 → 同范围合并去重重排 → 再审一次
      仍不足 → NO_ANSWER
      充分 → 同一证据集合 + 回答风格快照 → 生成
  → 引用校验 → 原有会话版本校验 → 平台发送 / 回问 / 人工处理
```

单跳 floor 为 `max(0.02, top1 × 10%)`。运营服务沿用它原有的
`reranker_score_normalized` 分数语义，与外部 RAG 模型的原始分值不可横向比较；排名和
分数只说明相关性，不表示事实正确概率。渠道最低证据阈值继续生效。

多跳来源检查覆盖全部已选证据；灰区模型审核也看到全部已选片段。Gate 放行后不再
删选上下文，Deep Agent 的只读工具也不能额外扩张证据范围。Trace 可以核对审核与生成
的 chunk IDs。答案实际使用的引用必须是该集合的有效子集，不会为凑齐数量伪造引用。

当前运营后端保留 FastEmbed / Qdrant；正文解析、分块和已发布索引继续使用运营已有
实现。这是针对在线回答核心与业务衔接的兼容移植，独立 RAG 的语义分块、多 embedding
视图、ANN 切换等功能没有在本次整体搬入。两边也不会实时自动同步代码。

## 在后台设置人设

进入 **知识与回复 → 知识库 → 回答风格**。修改助手名称、公司名称、回答风格和问候语，
保存后用于后续新请求，无须重新上传知识或重建索引。默认公司为 **智慧驱动**；
**周周有课**是课程系列名称。配置持久保存在 RAG SQLite 的当前知识库范围内。

可参考的风格：

> 以智慧驱动答疑助手的身份自然交流。先直接回答，简单问题用一小段，复杂问题按需列
> 步骤。用户问概览时给几个相关例子，不反复询问偏好，不每次都以问题结尾。

风格设置仅影响表达，不能新增业务事实、价格、时效、报名承诺或工具权限。事实始终
以已审核证据为准，不能假装真人或声称完成了没有执行的动作。
请求开始时读取不可变风格快照；中途修改不会改变正在生成的回答。Trace 只记配置哈希
和提示词版本，不保存完整自定义风格。

后台接口为管理员保护的 `GET /api/rag/answer-profile` 与
`PUT /api/rag/answer-profile`，使用运营配置中的固定知识库，忽略 URL 中伪造的其他库
参数。Python 管理端提供对应的
`/rag-admin-api/v1/knowledge-bases/{id}/answer-profile`，沿用原有 Bearer 认证。

模型配置继续走运营系统的统一模型配置或已有 RAG 环境变量。此次不覆盖 API Key，
也不把开发者本机的 DeepSeek 密钥写入 GitHub。

## 怎么验证一次接入

先在隔离数据目录测试：上传一份资料，等到 `READY_FOR_TEST`，选择该文档进入小智测试，
确认答案与引用，再沿用原来的发布按钮。正式问答只看到已发布版本；测试成功不等于
已经发布，上传完成也不等于正式用户可检索。

建议至少比较：有答案的改写问法、业务概览、接着上轮的短问句、没有对应资料的准确价格、
真正缺对象的问题、主动要求人工和评论知识不足。检查每条回答对应的 Trace：
问题类型、两轮检索、selected/discarded、Gate 审核 IDs、生成 IDs 和实际引用。

代码、自动回归、CI、运行部署与真实平台验收分别记录。自动化 fixture 通过不代表真实
公司语料的准确率，真实平台发送必须沿用原有权限和操作流程。
