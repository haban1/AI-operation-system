本次完成的是“稳定采集和稳定回复”的服务端核心闭环，未开启真实平台自动发送：

1. 建立 `message_events` 消息事件账本、`reply_batches` 回复批次、`reply_attempts` 发送尝试、通道检查点和通道健康状态；

3. 同一会话使用稳定 `conversation_namespace` 归类消息、上下文、事件和批次；
4. 同一会话连续入站消息在 `PENDING / GENERATING / READY` 阶段合并；
5. `READY` 旧答案遇到新消息时，旧回复 Job 在同一事务中取消；
6. `SENDING` 阶段到达的新消息创建第二个 `PENDING` 批次，不混入正在发送的旧批次；
7. 回复 Job 创建前、Agent 领取前都校验会话版本，旧答案不能进入发送；
8. 同一批次发送使用 `reply_attempts` 记录尝试，defer 后创建新 attempt，不复用旧 attempt；
9. 租约过期、服务重启或缺少可靠回执时进入 `SEND_UNCERTAIN / NEEDS_CONFIRMATION`，禁止自动重发；
10. 只有可靠平台回执才进入 `COMPLETED / VERIFIED` 并写入业务完成时间；
11. 功能开关关闭时继续走原 V1 回复路径，便于灰度和快速回退；

### 0.3 V2 回复批次状态机

```text
PENDING
  → GENERATING
  → READY
  → SENDING
  → COMPLETED                可靠发送回执
  → SOURCE_GONE              已确认源消息不存在
  → SEND_UNCERTAIN           发送结果不确定，等待人工核对

GENERATING + 新消息
  → 原生成结果失效
  → PENDING

READY + 新消息
  → 取消旧 REPLY Job
  → 合并新消息
  → PENDING

SENDING + 新消息
  → 旧批次继续完成/核对
  → 新消息建立第二个 PENDING 批次

SENDING + 页面明确不可用且确认未发送
  → attempt=NOT_SENT
  → batch=PENDING
  → 等待下一轮采集，不在本次请求中死循环

SENDING + 缺少可靠回执/租约过期/进程重启
  → attempt=SEND_UNCERTAIN
  → batch=SEND_UNCERTAIN
  → job=NEEDS_CONFIRMATION
  → 禁止自动重发
```

## 1. 执行目标

在不推倒现有知识库、回复引擎、会话版本和 `agent_jobs` 基础的前提下，完成以下改造：

1. 私信和评论形成两个独立业务通道；
2. 私信不再只依赖未读红点；
3. 每条消息使用稳定 ID 去重和同步；
4. 私信列表重新排序后仍能通过会话 ID 找到正确用户；
5. 用户在 AI 生成或发送过程中继续发消息时不会漏采或发送过时回复；
6. 同一会话连续消息合并，不同会话安全并发；
7. 私信和评论独立排队、独立页面、独立锁和独立健康状态；
8. 历史补采消息只入库，不触发重复自动回复；
9. 平台发送结果不确定时禁止盲目重试；
10. 在每天约 300 条事件规模下持续稳定运行。

最终验收不是“测试能跑通一次”，而是满足：

```text
不发错人
不静默漏采
不重复自动发送
不把同步失败显示成空消息
服务重启可恢复
平台回执不确定时可安全停住
```

## 7. 阶段 2：消息事件账本和检查点

### 7.1 数据库迁移

新增或等价实现：

```text
message_events
reply_batches

channel_runtime_states
```

对现有 `messages` 保持兼容：

- 第一阶段允许双写；
- Web 仍可从现有 `messages` 读取；
- 新账本验证稳定后再切换读取来源；
- 不立即删除 `reply_text` 等旧字段。

### 7.2 幂等约束

优先建立：

```text
UNIQUE(platform_code, account_id, channel_type, platform_message_id)
```

无平台消息 ID 时使用：

```text
message_fingerprint + identity_confidence
```

低可信指纹不得直接进入自动发送。

### 7.3 事务边界

单次消息同步事务：

```text
BEGIN
→ UPSERT conversation
→ INSERT/IGNORE message_event
→ 更新 reply_disposition
→ 更新 conversation version
→ 创建或更新 reply_batch
→ 更新 collection_checkpoint
COMMIT
```

检查点必须与消息落库处于同一可验证事务边界，不能先更新检查点再保存消息。

### 7.4 SQLite 并发处理

当前已启用 WAL 和 busy timeout，仍需补充：

- 所有事务保持短小；
- 禁止在事务中等待 AI 或浏览器；
- 对高频写操作使用统一写入服务；
- 对 `database is locked` 做有限重试和指标记录；
- 测试使用独立临时数据库，禁止多个测试共享运行库。

### 7.5 阶段测试

必须通过：

1. 相同 messageId 重复插入只保留一条；
2. 两个采集器同时发现同一消息只生成一个有效回复批次；
3. 数据库写失败时检查点不前进；
4. 写入后进程崩溃，重启重复扫描不重复创建发送任务；
5. 历史事件入库但 `reply_disposition=NOT_REQUIRED`；
6. 同名用户、不同 conversationId 不合并。

- 独立通道锁；
- 独立失败计数；
- 独立最后完整同步时间。

### 8.3 页面隔离

推荐：

```text
一个 BrowserContext
├── privatePage
└── commentPage
```

必须删除或隔离所有依赖“当前活动 Page”的共享可变状态。每个适配器操作必须显式接收目标 `page`。

### 8.4 队列领取规则

私信队列内部：

```text
ORDER BY first_pending_at, id
```

评论队列内部：

```text
ORDER BY first_pending_at, id
```

私信和评论不互相排序，各自由对应 Worker 领取。

生成任务与浏览器发送任务可以并行，但同一通道的页面 DOM 写操作必须加锁。

### 8.5 资源配额

建议初始：

```text
AI_PRIVATE_RESERVED=1
AI_COMMENT_RESERVED=1
AI_SHARED_BURST=1
BROWSER_OPERATION_CONCURRENCY=2～3
ACCOUNT_CHANNEL_SEND_CONCURRENCY=1
```

保留资源意味着一个通道积压时不能完全饿死另一个通道。空闲配额可借用，但不能中断已开始的发送动作。

### 8.6 阶段测试

1. 私信任务运行时评论任务可以领取；
2. 评论任务异常时私信任务继续运行；
3. 两个 Worker 不操作对方页面；
4. 同一通道两个写操作不会同时点击；
5. 关闭私信通道不影响评论通道；
6. 关闭评论通道不影响私信通道；
7. 旧 `COLLECT_MESSAGES` 在迁移期间不会与新任务重复采集。

## 9. 阶段 4：抖音私信双路径采集

抖音先做，其他平台在抖音通过后复用框架。

### 9.1 保留未读快速路径

保留红点优先扫描，但把现有：

```text
无红点 = 不采集
```

改成：

```text
无红点 = 不进入快速路径，但仍可进入最近会话核对
```

### 9.2 新增最近会话核对

按检查点扫描：

- 最近活跃会话；
- 上次不完整会话；
- 服务启动恢复窗口；
- 账号回复为最新预览但本地缺失来消息的会话。

### 9.3 时间线提取

每次打开会话读取：

```text
conversationId
messageId
direction
content
eventTime
sender
```

要求两次或多次稳定快照；具体次数和间隔通过真实页面测试配置。

### 9.4 历史处理规则

```text
来消息后面已有账号回复
→ 保存来消息和账号回复事件
→ 标记 ALREADY_HANDLED
→ 不创建自动回复任务
```

```text
来消息尚无账号回复且满足新消息证据
→ 标记 REQUIRED
→ 创建或合并私信回复批次
```

### 9.5 空结果规则

仅当所有目标会话均稳定完成扫描时允许返回：

```text
SYNC_COMPLETE_NO_NEW_EVENTS
```

任一会话标题缺失、时间线不稳定或列表加载不完整时返回：

```text
SYNC_INCOMPLETE_RETRYING
```

### 9.6 Amy 修复验证

对已确认案例执行只读、限定范围核对：

```text
打开 Amy 稳定会话
→ 识别“怎么联系我们”来消息
→ 识别其后账号回复
→ 补录来消息
→ 标记已处理
→ Web 显示
→ 不生成自动回复任务
```

该修复必须先在测试数据库和只读诊断下验证，禁止直接触发真实自动回复。

## 10. 阶段 5：稳定定位、三次读取和发送保护

### 10.1 稳定 ID 优先定位

改造 `openPrivateConversationForPayload()` 或新增 V2 方法：

```text
优先 conversationUrl
→ 优先 conversationId
→ 平台 userId
→ 分页/滚动查找稳定 ID
→ 昵称和预览仅作辅助
```

普通业务消息缺少稳定 conversationId 时，默认禁止自动发送。

### 10.2 页面重新排序测试

构造：

```text
用户1任务生成时排第1
用户2、用户3发消息后用户1排第3或移出可见区域
```

必须验证：

- 不点击旧行号；
- 能滚动或直接打开 conversationId；
- 进入后检查原 messageId；
- 发给用户1，不发给用户2或用户3。

### 10.3 三次读取

回复流程改为：

```text
读取 A：进入会话后，建立当前批次
→ AI 生成
→ 读取 B：发送前检查版本和新增来消息
→ 发送并验证
→ 读取 C：发送后检查同时到达的新消息
```

### 10.4 发送前核验

硬性校验：

```text
accountId 一致
channelType=PRIVATE_MESSAGE
conversationId 一致
sourceMessageIds 存在
方向为 incoming
conversationVersion 一致
时间线稳定
没有新增未覆盖消息
没有后续账号回复已覆盖本批次
```

### 10.5 写后状态机

```text
未点击发送且前置失败
→ 可安全重试

已点击且取得可靠新增己方气泡/平台 ID
→ SUCCESS

已点击但无法确认
→ NEEDS_CONFIRMATION，禁止自动重发

平台明确拒绝且确认未产生发送
→ FAILED/RETRYING，按错误分类处理
```

### 10.6 阶段测试

必须覆盖：

1. AI 生成期间当前用户发补充消息；
2. AI 生成期间其他用户发消息导致列表重排；
3. 点击前 1 个瞬间到达新消息；
4. 点击后到达新消息；
5. 点击成功但网络响应丢失；
6. 输入框清空但没有新增气泡；
7. 新增气泡出现但页面刷新；
8. conversationId 不一致；
9. messageId 不存在；
10. 同名用户多行匹配；
11. 页面被评论 Worker 错误导航的防护；
12. 服务在发送前后重启。

## 11. 阶段 6：连续消息批次与上下文增强

### 11.1 批次聚合

同一会话所有尚未被账号回复覆盖的连续来消息进入一个批次：

```text
用户：你们在哪里？
用户：周末营业吗？
用户：需要预约吗？
```

生成一个回复批次，不生成三个互相独立的发送任务。

### 11.2 旧任务失效

新来消息入库后：

- conversation version 增加；
- 原生成任务如果未发送则取消或重新生成；
- 已经发送的批次记录 `covered_through_event_id`；
- 新消息进入下一批次，不重复覆盖旧事件。

### 11.3 上下文包

将当前部分“最近 6 条”策略增强为：

```text
最近 6～10 轮原始消息
+ 长期摘要
+ 用户事实记忆
+ 未解决问题
+ 相关历史片段
+ 当前连续消息批次
```

不能把全部历史原文直接放进提示词。

### 11.4 话题判断

输出：

```text
CONTINUE_TOPIC
NEW_TOPIC
MIXED_TOPIC
UNCERTAIN
```

“新消息”和“新话题”不可混用。

### 11.5 回答覆盖校验

每次生成保留：

```text
输入问题列表
已回答问题列表
未回答问题列表
知识命中列表
是否使用上下文
是否需要澄清
是否需要转人工
```

多问题被截断或只回答部分时，必须明确提示或进入下一步澄清，不能静默遗漏。

### 11.6 阶段测试

1. 连续三条消息合并一次回复；
2. 第一条生成中第二条到达，旧回复失效；
3. 隔几天发送“那高级版呢”能承接旧话题；
4. 隔几天发送“你们公司在哪里”识别为新话题；
5. 同一句文字发送两次但 messageId 不同，保留两条事件；
6. 同名用户上下文不串；
7. 低可信身份不启用长期记忆；
8. 8 个以上问题的截断结果对用户可见；
9. 知识缺口不编造；
10. AI 超时使用安全知识回退或转人工。

## 15. 阶段 10：上线策略

### 15.1 第一级：只读观察

## 16. 回滚方案

### 16.1 功能回滚

通过功能开关分别关闭：

```text
私信 V2 采集
私信 V2 自动发送
评论 V2 采集
评论 V2 自动发送
上下文增强
Web 新状态
```

关闭自动发送不应停止事件入库和人工查看。

### 16.2 数据回滚

新表只追加，不在初期删除旧表字段。回滚时：

- 保留 `message_events` 作为审计记录；
- 停止新 Worker；
- Web 可暂时切回旧 `messages` 视图；
- 已有发送尝试不得删除；
- `SEND_UNCERTAIN` 不得因回滚自动重排。

### 16.3 浏览器回滚

- 关闭双 Page Worker；
- 释放 privatePage 和 commentPage；
- 恢复旧单页面前确认没有运行中发送动作；
- 保留页面截图和任务结果。

### 16.4 紧急停机条件

出现以下任一情况立即关闭对应通道自动发送：

```text
发错目标 1 次
明确重复发送 1 次
账号身份不一致
平台页面结构无法确认
发送不确定任务持续增长
同一会话并发写入
数据库持续锁死
大量历史消息被错误标记为待回复
```

处理：

```text
查看账号登录状态
→ 查看 privatePage 页面状态
→ 查看失败会话 ID
→ 保留旧检查点
→ 执行只读重试
→ 连续失败后转人工
```

禁止：

```text
把数据库 0 条直接显示为暂无私信
```

### 20.2 回复发送不确定

处理：

```text
停止自动重试
→ 打开目标会话
→ 查找新增己方气泡或平台消息 ID
→ 已发送则标记成功
→ 确认未发送后才允许重新排队
```

### 20.3 会话无法定位

处理：

```text
检查 conversationUrl
→ 检查 conversationId
→ 滚动/分页查找
→ 检查账号身份
→ 仍找不到则 MANUAL_REQUIRED
```

禁止使用同名用户替代。

### 20.4 数据库锁冲突

处理：

```text
确认是否存在长事务
→ 查看并发写 Worker
→ 有限重试
→ 检查检查点是否未前进
→ 必要时暂时降低写并发
```

### 20.5 评论通道异常

只关闭评论通道，私信继续运行；私信异常时同理。

## 22. 最终执行结论

本项目不需要新增大量“大模型 Agent”，也不需要把五个平台全部放进一个大任务。正确实施方式是：

```text
一个中央调度系统
+ 私信和评论两类独立持久化队列
+ 每个平台账号两条逻辑通道
+ 小任务领取和有限并发
+ 稳定 ID 定位
+ 完整消息事件账本
+ 发送前后核验
+ 失败可见和可恢复
```

执行时必须优先保证安全性和可恢复性，不能为了“看起来更快”而取消目标核验、回执确认或历史补采保护。

上线后的稳定性承诺应表述为：

> 在平台页面或 API 可访问的前提下，消息最终会被同步和处理；如果平台、网络、登录或页面结构导致任务无法完成，系统会保留检查点，对读取、定位等可安全重复的操作进行有限重试，或者转人工；一旦发送结果不确定则停止自动重发并进入人工确认。所有异常都要明确显示，不能把失败伪装成暂无消息或回复成功。
