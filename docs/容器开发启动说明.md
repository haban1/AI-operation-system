# 容器开发启动说明

## 当前已接入微信的启动方式

当前微信客服已迁到 8080 原生机器人；8000 与 PostgreSQL 已停用。天河与统一模型网关启动时同时加载微信网络配置：

```powershell
docker compose -f compose.yaml -f compose.wechat.yaml up -d --build --wait --wait-timeout 240
docker compose -f compose.yaml -f compose.wechat.yaml restart web rag
```

打开 http://127.0.0.1:3100，使用“知识库”与“微信客服”模块。微信资料在 8080 原生知识库维护；工作空间的微信客服嵌入同一后台。前端修改后刷新页面；服务端修改后重启对应服务。在线模型统一在天河“企微及 AI”配置，首次接入见 [统一模型配置](统一模型配置.md)。天河顶部五平台总开关不控制微信服务。

当前同机部署已开启 WECHAT_ROBOT_ADMIN_FOLLOW_HOST：从本机或局域网访问天河时，微信后台跟随天河使用相同主机的 8080 端口，保持内嵌登录状态。机器人改到另一台主机时应关闭此配置，并重新配置访问地址。

首次迁入、备份和回退步骤见 [微信原生客服迁移-20261019.md](微信原生客服迁移-20261019.md)。以下单独的 `docker compose` 命令适用于不接微信的基础开发模式；在当前接入环境请带上上述两个 `-f` 参数，防止重建 Web 时丢失微信管理地址。

Docker Compose 启动 Web、RAG，以及由 Web 总开关管理的模拟 Local Agent。要求 Docker Desktop 使用 Linux containers；无需在 Windows 安装项目的 npm/Python 依赖。初始化脚本使用 Node 24+。

## 首次启动

在 `project` 目录运行：

```powershell
node scripts/init-docker-dev.mjs
docker compose up -d --build --wait --wait-timeout 240
```

打开 http://127.0.0.1:3100 ，初始账号 `admin`，密码 `admin123`。可在 `.env.docker` 修改密码。初始化脚本生成随机服务密钥，重复执行不会覆盖配置。

首次启动创建全新演示数据库，五个平台及运行总开关为关闭状态；正式 RAG 知识库为空。上传、处理、测试并发布知识后才能进行正式知识问答。没有已发布知识时，RAG 的 `NOT_READY` 是预期状态。

## 修改源码

源码直接挂载自本机。修改前端 HTML/CSS/JS 后刷新浏览器；修改服务端后执行：

```powershell
docker compose restart web
docker compose restart rag
```

修改 package-lock.json、pyproject.toml、uv.lock 或 Dockerfile 后执行：

```powershell
docker compose up -d --build --wait --wait-timeout 240
```

本配置使用明确的重启命令，不依赖 Windows 共享目录的文件监听事件。npm 依赖和 Python 虚拟环境保存在 Linux 镜像中。

## 构建时 `npm ci` 失败的排查（宿主代理）

现象：`docker compose ... up -d --build` 时，web 镜像构建停在 `RUN npm ci --no-audit --no-fund`，报

```
npm error Exit handler never called!
npm error This is an error with npm itself. Please report this error at:
```

rag / wechat 因命中缓存不受影响，只有 web 会失败。

原因（2026-10-13 深挖确认，比"未配置代理"更准确）：本机 Windows 系统代理指向 `127.0.0.1:7897`（Clash Verge 的默认混合端口），
**但该代理进程当时没有运行，7897 端口无人监听**；而 Docker Desktop 的配置是 `proxyHttpMode = "system"`，
并启用容器透明代理（`vpnKitTransparentProxy = true` + `containersOverrideProxyTransparentPorts = "80,443"`）。
两者叠加的结果是：**容器访问 80/443 的流量被统一转送到这个死端口**，TLS 握手发出去就立刻被切断。

症状极具迷惑性：容器内 DNS 解析正常、`curl -v` 甚至打印 `Connected to ... port 443`，但任何 `https://` 都失败。
npm 在这种情况下会给出上面那句与网络无关的误导性报错。

判别方法 —— 看是"连不上"还是"TLS 被切断"：

```sh
# 容器内
curl -v -sS -o /dev/null --max-time 8 https://www.baidu.com 2>&1 | grep -E "Connected|TLS|error"
# 故障态特征：Connected 之后紧跟 "TLS alert, decode error" + "unexpected eof while reading"
```

宿主侧比对"系统代理端口"与"实际在监听的端口"，两者不一致即可确诊：

```powershell
netstat -ano | findstr LISTENING | findstr "7897"
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyServer
```

确认方法（在任意运行中的容器内执行，`<代理端口>` 取宿主代理设置里的端口）：

```sh
npm view react version                                              # 卡住 / 无输出
npm view react version --https-proxy=http://host.docker.internal:PORT # 正常输出版本号
```

解决办法：构建时显式透传代理。BuildKit 预定义了这些参数，Dockerfile **不需要**声明 `ARG`：

```powershell
docker compose -f compose.yaml -f compose.wechat.yaml build `
  --build-arg HTTP_PROXY=http://host.docker.internal:PORT `
  --build-arg HTTPS_PROXY=http://host.docker.internal:PORT `
  --build-arg NO_PROXY=localhost,127.0.0.1 web
docker compose -f compose.yaml -f compose.wechat.yaml up -d --wait --wait-timeout 240
```

根治办法（二选一，2026-10-13 均已实测）：

1. **让系统代理指向的端口重新可用** —— 启动 Clash Verge（本机系统代理就是它的默认混合端口 7897）。
   实测：端口一有服务监听，**所有容器的 https 立刻恢复正常，不需要重启 Docker Desktop**
   （透明代理是运行时实时转发的）；验证时容器内 `https://www.baidu.com` 由 TLS EOF 变为 `200`。
2. **让容器出网彻底绕开代理规则（本机已采用并验证通过，2026-10-14）** —— 把 Docker Desktop 设置里的
   `containersOverrideProxyTransparentPorts` 由 `80,443` 清空为 `""`。这是官方语义下最小、最精准的改法：
   官方文档明确「Docker Desktop 只对 `transparentPorts` 里列出的端口接管容器 TCP 连接；
   **不配置则运行中容器的流量完全绕过 `containersProxy`**」。清空后容器出网走直连，
   从此与宿主代理软件开没开无关。

   操作步骤（**顺序不能反**）：

   ```powershell
   # 1. 先完全退出 Docker Desktop —— 否则它退出时会把内存里的设置写回，覆盖你的修改
   #    （托盘右键 Quit，或先停掉容器再结束进程）
   # 2. 编辑 %APPDATA%\Docker\settings.json，把该字段改成空字符串：
   #      "containersOverrideProxyTransparentPorts": ""
   # 3. 重新启动 Docker Desktop，容器会自动恢复
   ```

   **不要改 `proxyHttpMode`**：它只接受 `system` / `manual`，历史上被填成布尔值或空值会导致
   Docker Desktop 启动失败并报 `proxyHttpMode must be a boolean value`。

   本机实测结果（2026-10-14，改完重启 Docker Desktop 后）：

   | 验证项 | 修复前 | 修复后 |
   |---|---|---|
   | 容器内 → `https://www.baidu.com` | TLS EOF | **200** |
   | 容器内 → `https://dns.weixin.qq.com` | TLS EOF | **404**（HTTP 层正常响应）|
   | 通用容器（postgres:16-alpine）→ baidu | FAIL | **OK** |
   | 微信机器人 iPad 二维码接口 | 500「获取二维码失败」| **200 + uuid/data62** |
   | iPad 协议服务 mmtls panic 次数 | 15 次 | **0 次** |
   | 微信 `wechat-server` token 刷新 | `EOF` | 连续 `access token refreshed` |

   备份文件：`%APPDATA%\Docker\settings.json.bak-20261013-qr`（回滚只需把该字段改回 `"80,443"`）。

注意三点：写在 shell 里的 `HTTP_PROXY` / `HTTPS_PROXY` **不会**被 Compose 自动带进构建，必须用 `--build-arg`；
日常开发（源码为只读挂载、改前端刷新浏览器、改服务端 `restart web`）不需要重建镜像，不受此问题影响；
这个坑是**机器级**的，会同时影响本机所有 Docker 项目栈，排查其他容器"莫名连不上外网"时可直接套用上面的判别方法。

## 日常命令

```powershell
docker compose ps
docker compose logs -f --tail 100 web rag
docker compose exec web sh
docker compose exec rag sh
# 独立临时容器运行已有 Node 测试，隔离开发服务的数据及运行锁：
docker compose run --rm --no-deps -e RAG_BASE_URL= -e RAG_FORMAL_ROUTING_ENABLED=false -e RAG_ADMIN_ENABLED=false -v /app/data -v /app/logs web node scripts/run-tests.mjs --test --test-concurrency=1 test/security-runtime.test.js test/runtime-recovery.test.js
# 停止，保留数据：
docker compose down
# 再次启动：
docker compose up -d --wait --wait-timeout 240
```

`down -v` 会删除开发数据库、上传文档和日志，只有明确要清空开发环境时才使用。

上述测试覆盖登录安全和进程恢复。仓库完整测试集还包含读取 Windows 启动脚本、本地 `.env`、启动 Windows Chrome 的用例，不能将当前 Linux 开发镜像视为完整 Windows 验收环境。

## 数据、模型和配置

- Compose 项目名为 `tianhe-dev`，管理后台发布在本机 `3100`。RAG 使用容器网络中的 `rag:18080`，通过 Web 代理访问，不占用宿主机的 `18080` 端口。
- `tianhe-dev_web_data` 保存开发 SQLite 数据库和配置加密密钥；`tianhe-dev_rag_data` 保存上传文件、知识库和 Qdrant 本地索引；`tianhe-dev_web_logs` 保存 Agent 日志。
- 交接包中的业务数据库和 `.env` 不挂载进容器。容器只读取独立的 `.env.docker`，该文件已被 Git 忽略。
- `rag-service/models` 只读挂载交接包内的 embedding/reranker 模型，不导入原知识库。
- 默认 Web AI 为 `mock`，embedding/reranker 使用真实本地模型。统一模型接口在模拟模式下不发起在线生成。
- 需要在线模型时，在天河“企微及 AI”启用在线模式，填写接口、密钥与模型。Compose 中 RAG 和微信 Agent 通过统一内部接口使用该配置，保存后无需重启。旧的独立模型变量仅用于未启用统一模式的独立部署。
- 修改 `.env.docker` 后执行 `docker compose up -d --force-recreate --wait --wait-timeout 240`；仅 `restart` 不会重读容器环境变量。

## 真实平台联调

当前配置固定 `RPA_MODE=simulated`。开启总开关后启动容器内的模拟 Agent，支持任务编排和模拟执行。Windows 原生文件选择器、人工登录的 Chrome Profile、真实平台发布/回复不能在这个 Linux 容器配置中直接使用。模拟素材可使用容器路径 `/app/sample-material/...`。

真实平台联调应让 Agent 运行在 Windows 上。目前 Web 的 Agent 代理仍有固定 `127.0.0.1` 的地址，连接宿主机 Agent 还需要改造地址配置及管理逻辑，不能仅将 RPA_MODE 改成真实模式。该改造与当前容器开发启动独立。
