# 知识库模块架构与安全检索设计方案 V1.0

- **项目**：天河 AI 数字员工运营平台
- **版本**：V1.0
- **日期**：2026-08-19
- **状态**：待评审 / 可进入分阶段实施
- **适用代码库**：`D:\code\AI数字运营2`
- **核心目标**：在知识量持续增长的情况下，保证知识可追溯、检索可扩展、回复可解释，并在不确定时严格停止自动回复。

---

## 1. 结论先行

当前知识库适合少量 FAQ 验证，但不适合直接扩展到大规模生产：它从 SQLite 全量读取已发布 FAQ，在 Node.js 中使用关键词和中文双字 Dice 相似度排序，只使用 Top1，再以固定阈值 `0.58` 决定是否自动回复。该方式会随数据量增加同时放大四类问题：**性能下降、相似问题互相争抢、错答率上升、问题难以追溯**。

本方案不在现有 `knowledge` 表上简单追加向量字段，而是把知识库拆为五层：

1. **知识治理层**：知识实体、不可变版本、范围、风险、审核、有效期；
2. **可靠索引层**：事务 Outbox、幂等索引任务、版本化索引、校验和与回滚；
3. **混合检索层**：精确匹配、别名、全文/BM25、向量、元数据过滤、融合与重排；
4. **安全决策层**：置信度、Top1/Top2 间隔、多意图、冲突、时效和风险门禁；
5. **评测观测层**：检索链路日志、黄金集、回放、质量指标、灰度和告警。

> “不会出错”不能被技术上绝对承诺。可实现的工程目标是：**不满足证据条件时不自动回复；任何自动回复都能追溯到已审核、有效、范围匹配且索引版本一致的知识；错误可以被检测、阻断、回放和快速回滚。**

### 1.1 最终推荐架构

```text
管理端 / 导入任务 / 知识缺口
          │
          ▼
┌─────────────────────────────────────┐
│ Source of Truth                    │
│ PostgreSQL（过渡期可继续 SQLite）   │
│ item/version/scope/review/outbox    │
└─────────────────┬───────────────────┘
                  │ 同一事务写 Outbox
                  ▼
┌─────────────────────────────────────┐
│ Index Worker                        │
│ 清洗 → 切块 → embedding → 建索引     │
│ 校验 checksum → 激活 → 延迟删除旧版  │
└──────────────┬───────────────┬──────┘
               │               │
        ┌──────▼──────┐ ┌──────▼──────┐
        │ 全文/倒排索引 │ │ 向量索引     │
        │ FTS/OpenSearch│ │ pgvector/OS │
        └──────┬──────┘ └──────┬──────┘
               └───────┬───────┘
                       ▼
查询上下文 → 规范化 → 范围过滤 → 并行召回 → RRF 融合 → 重排
                       │
                       ▼
             安全门禁 / 决策引擎
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
  模板直接回复       Qwen 有据生成       澄清/人工/知识缺口
```

### 1.2 技术选型原则

- **当前过渡期**：SQLite + FTS5 + 新数据模型 + Outbox；先解决正确性和可追溯性，不强制立刻引入新基础设施。
- **中长期生产**：PostgreSQL 作为唯一事实源；OpenSearch 同时承载 BM25、过滤和向量检索，或 PostgreSQL + pgvector 作为中等规模方案。
- **禁止把搜索索引当主数据库**：索引可以重建，不能成为审核状态、有效期和版本关系的唯一事实来源。
- **禁止数据库与索引直接双写**：所有索引变更必须从事务 Outbox 异步投递，失败可重试。
- **禁止仅依赖模型置信度**：自动回复由确定性规则、元数据、证据质量和经离线校准的阈值共同决定。

## 2. 当前实现与主要风险

### 2.1 当前链路

现有关键实现：

- `D:\code\AI数字运营2\src\services\knowledge.js`
  - `normalizeText()`：简单同义词替换和符号清理；
  - `scoreKnowledge()`：精确问题、关键词命中、问题双字 Dice、答案双字 Dice 取最大值；
  - `searchKnowledge()`：查询所有允许分类下的 `PUBLISHED` 数据，在 Node.js 全量评分，返回 Top3。
- `D:\code\AI数字运营2\src\server.js`
  - 只使用 Top1；
  - Top1 分数低于 `AUTO_REPLY_THRESHOLD=0.58` 时形成知识缺口；
  - 高于阈值后调用 Qwen 组织回复。
- `D:\code\AI数字运营2\src\services\qwen.js`
  - Qwen 只接收唯一一条知识；
  - 提示词要求标准答案完整出现，再做回复长度保护。
- `D:\code\AI数字运营2\src\services\knowledge-import.js`
  - 提供文档导入、清洗、相似项判断和预览。

### 2.2 已确认的错误模式

| 场景 | 当前表现 | 根因 |
|---|---|---|
| “我想参加社区活动，怎样报名？” | “近期有什么社区活动？”可能排在“活动报名”之前 | 通用关键词权重过强，缺少意图和重排 |
| 简体问题匹配繁体知识 | 相似度可能低于阈值 | 规范化不支持简繁、实体与同义表达 |
| “近期有什么活动，收费吗？” | 只用 Top1，遗漏第二意图 | 没有多意图拆分和证据覆盖判断 |
| 知识持续增长 | 每次查询扫描全部已发布行 | O(N × 文本长度)，无倒排/向量索引 |
| 修改已发布知识 | 修改可直接影响线上 | 缺少不可变版本和重新审核流程 |
| 测试知识 | `SYSTEM_TEST` 可处于 `PUBLISHED` | 检索未显式排除测试来源 |
| 索引失败或内容过期 | 当前无对应门禁 | 无索引状态、有效期和版本一致性检查 |

### 2.3 必须保留的现有能力

新设计不能破坏下列能力：

- 公共知识与五个平台专属知识的范围控制；
- 平台评论/私信长度限制；
- 导入预览、重复/相似判断、审核与知识缺口处理；
- Qwen 只能依据已检索证据生成；
- 当前 SQLite 单机部署可以继续运行，并可逐步迁移。

## 3. 设计目标、非目标与安全原则

### 3.1 设计目标

1. 知识从几十条扩展到百万级时，业务代码和数据模型不推倒重来；
2. 任何线上知识都具有稳定 ID、不可变版本、审核记录、范围、有效期和来源；
3. 检索同时兼顾精确性、语义召回、中文表达差异和平台隔离；
4. 自动回复只发生在证据充分、无冲突、风险允许、版本一致的情况下；
5. 索引失败、模型失败、配置错误、数据过期时默认进入澄清或人工，不“猜答案”；
6. 每次检索和决策可回放，能够回答“为什么匹配到这条知识”；
7. 支持无停机重建索引、灰度切换和一分钟级逻辑回滚。

### 3.2 非目标

- 不把动态活动余量、实时价格、用户资格等实时数据直接写成长期 FAQ；
- 不允许 LLM 自行决定发布知识、突破审核或平台范围；
- 不在第一阶段一次性替换全部数据库和搜索基础设施；
- 不以“召回更多”为理由降低自动回复安全门槛。

### 3.3 强制安全原则

1. **Fail Closed**：异常、不确定、缺上下文、冲突、过期、版本不一致时不自动回复。
2. **事实源唯一**：数据库是状态和版本事实源，索引只是可重建副本。
3. **发布不可变**：已发布版本禁止原地修改，修改必须生成新草稿并重新审核。
4. **范围前置**：租户、平台、账号、消息类型、环境、有效期过滤必须进入检索后端查询条件；应用层再进行第二次校验。
5. **最小证据**：回复中的事实必须由所选证据覆盖；缺失部分不得由模型补全。
6. **动态数据分离**：实时事实从业务 API 获取，并携带时间戳、TTL 和错误策略。
7. **配置版本化**：归一化规则、embedding 模型、索引 schema、阈值和重排器全部带版本。
8. **测试数据隔离**：`SYSTEM_TEST`、非生产环境和测试租户永远不参与生产检索。

### 4.1 职责约束

- `repository.js` 只管理事实源事务，不直接调用模型或搜索后端；
- retriever 只能返回候选，不得直接决定自动回复；
- `decision.js` 是唯一自动回复门禁；
- `answer-composer.js` 不得扩大证据范围；
- `answer-validator.js` 失败后不得回退到未经验证的模型文本；
- 管理端发布必须调用 `lifecycle.js`，禁止路由直接更新状态字段。

## 5. 知识分类与数据模型

### 5.1 知识类型

| 类型 | 用途 | 推荐处理 |
|---|---|---|
| `FAQ` | 稳定的一问一答 | 问题、别名、关键词、标准答案 |
| `DOCUMENT` | 政策、办事指南、长文档 | 文档版本 + 章节 + chunk |
| `STRUCTURED_FACT` | 地址、电话、办公时间等结构化事实 | 字段化保存，模板渲染 |
| `DYNAMIC_ACTION` | 活动余量、实时费用、订单状态等 | 保存连接器/动作定义，不保存易过期答案 |
| `PLAYBOOK` | 平台话术、处置流程 | 严格平台/账号/消息类型范围 |
| `TEMPLATE` | 确定性回复模板 | 无需 LLM 或仅允许插入受控变量 |

### 5.2 核心关系表

以下字段是逻辑模型。过渡期可用 SQLite 类型实现，中长期迁移到 PostgreSQL。

#### `knowledge_items`：稳定业务身份

| 字段 | 约束 | 说明 |
|---|---|---|
| `id` | UUID/ULID PK | 稳定 ID，不随版本变化 |
| `tenant_id` | NOT NULL | 租户隔离键；当前单租户也必须预留 |
| `knowledge_type` | enum | FAQ/DOCUMENT/... |
| `risk_level` | enum | LOW/MEDIUM/HIGH/PROHIBITED |
| `owner_team` | NOT NULL | 责任团队 |
| `active_version_id` | nullable FK | 当前线上唯一版本 |
| `lifecycle_status` | enum | DRAFT/REVIEWING/INDEXING/PUBLISHED/... |
| `created_by/created_at` | NOT NULL | 审计字段 |
| `updated_at` | NOT NULL | 管理元数据更新时间 |

索引：

- `(tenant_id, lifecycle_status)`；
- `(tenant_id, knowledge_type)`；
- `(tenant_id, active_version_id)` 唯一性和外键校验。

#### `knowledge_versions`：不可变内容快照

| 字段 | 约束 | 说明 |
|---|---|---|
| `id` | UUID/ULID PK | 版本 ID |
| `knowledge_id` | FK | 所属知识 |
| `version_no` | integer | 单知识递增，唯一 |
| `title/question/answer/content` | text | 按类型使用 |
| `normalized_question` | text | 按规则版本生成 |
| `normalized_hash` | char(64) | 精确去重与精确召回 |
| `keywords_json` | json | 受控关键词，不再使用逗号字符串 |
| `language` | text | 如 `zh-CN`、`zh-Hant` |
| `source_type/source_ref` | text | MANUAL/IMPORT/GAP/API 及来源引用 |
| `content_checksum` | char(64) | 内容完整性校验 |
| `normalizer_version` | text | 可重建 |
| `schema_version` | integer | 内容结构版本 |
| `valid_from/valid_to` | timestamp | 生效区间，结束时刻采用左闭右开 |
| `review_status` | enum | PENDING/APPROVED/REJECTED |
| `reviewed_by/reviewed_at` | audit | 审核追溯 |
| `index_status` | enum | PENDING/INDEXING/READY/FAILED |
| `index_generation` | text | 使用的索引代次 |
| `embedding_model/version` | text | 向量版本 |
| `created_by/created_at` | audit | 创建记录 |

强约束：

- `UNIQUE(knowledge_id, version_no)`；
- 发布后的版本内容不可更新，只能新增版本；
- `valid_to > valid_from`；
- `active_version_id` 只能指向 `APPROVED + READY` 且当前有效的版本；
- `source_type='SYSTEM_TEST'` 不允许被生产环境激活。

#### `knowledge_utterances`：问题别名与真实说法

| 字段 | 说明 |
|---|---|
| `version_id` | 对应知识版本 |
| `utterance` | 用户真实表达 |
| `normalized_text/hash` | 精确和近似检索 |
| `source` | MANUAL/LOG/MODEL_SUGGESTED/IMPORT |
| `review_status` | 模型建议必须人工确认后上线 |
| `weight` | 受限权重，不能绕过风险门禁 |

该表解决“报名怎么报”“我想参加”“繁简体”等多表达问题，避免把泛化关键词写入答案。

#### `knowledge_scopes`：范围控制

| 字段 | 说明 |
|---|---|
| `version_id` | 版本范围 |
| `tenant_id` | 强制 |
| `environment` | PROD/STAGING/TEST |
| `platform_code` | 空表示全部平台 |
| `account_id` | 空表示平台内全部账号 |
| `message_type` | COMMENT/PRIVATE_MESSAGE/ALL |
| `audience` | 可选人群范围 |
| `region_code` | 可选地域范围 |

要求：范围既写入索引文档，也在候选回源时再次校验。平台专属知识优先不是“加一点排序分”，而是**先过滤到合法范围，再按具体度排序**：账号 > 平台 > 公共。

#### `knowledge_documents` 与 `knowledge_chunks`

文档知识不直接把整篇文章作为一个 FAQ：

- document 保存文档身份、来源、文件 checksum、解析状态；
- chunk 保存章节路径、页码、段落序号、文本、token 数、父子关系；
- chunk 大小建议按语义段落切分，并设置少量重叠；
- 标题、章节名、表格表头必须随 chunk 进入索引；
- 答案证据应保留文档、版本、章节、页码或段落定位。

#### 可靠性与观测表

- `knowledge_reviews`：每次审核动作、意见、前后状态；
- `knowledge_outbox`：事务事件，字段含 `event_id/event_type/aggregate_id/version_id/payload/status/attempts/next_retry_at`；
- `knowledge_index_state`：版本、索引代次、文档数量、checksum、激活时间；
- `knowledge_retrieval_logs`：查询、上下文摘要、配置版本、决策、耗时和错误码；
- `knowledge_retrieval_candidates`：候选版本、各路分数、排序、拒绝原因；
- `knowledge_feedback`：人工判定、用户反馈、是否正确；
- `knowledge_eval_cases/runs`：黄金集和评测结果；
- `knowledge_gaps`：扩充为聚类、频次、示例、建议归属、处理版本和关闭依据。

### 5.3 数据量与分区策略

- 所有大表首列都带 `tenant_id`，避免未来补租户键导致全量迁移；
- 检索日志按月分区或按月归档，候选明细保留 30～90 天，聚合指标长期保留；
- 文档 chunk 与 embedding 分开存储，避免版本元数据行过大；
- 索引按租户量选择共享索引 + tenant filter，超大租户可独立索引；
- 禁止按“每个知识分类一个索引”无限拆分，以免产生大量小分片；
- 删除采用 tombstone + 异步清理，禁止直接硬删线上版本。

## 6. 知识生命周期与发布状态机

```text
DRAFT
  └─提交审核→ REVIEWING
                  ├─驳回→ REJECTED → 新建/修改草稿
                  └─通过→ APPROVED
                              └─创建 Outbox→ INDEXING
                                      ├─失败→ INDEX_FAILED（不可检索）
                                      └─校验通过→ READY
                                                    └─原子激活→ PUBLISHED
PUBLISHED
  ├─编辑→ 新 DRAFT（旧版继续服务）
  ├─到期→ EXPIRED（立即禁止服务）
  └─停用→ RETIRING → DISABLED
```

### 6.1 发布步骤

1. 在数据库事务内验证字段、重复项、范围、风险、有效期、答案长度和审核状态；
2. 创建不可变版本，写入 `knowledge_outbox(INDEX_VERSION)`；
3. worker 幂等消费：规范化、切块、生成 embedding、写入 staging 文档；
4. 按版本 ID、chunk 数和 checksum 读回验证；
5. 标记版本 `READY`；
6. 在事务内把 `knowledge_items.active_version_id` 指向新版本，写 `ACTIVATE_VERSION` 事件；
7. 检索候选必须回源确认仍为 active、有效且范围匹配；
8. 旧版本延迟保留，确认无流量和可回滚后再写 tombstone 清理。

这样即使出现索引早于数据库或数据库早于索引的短暂时序差异，也只会导致“暂时不自动答”，不会接受错误版本。

### 6.2 编辑、停用和到期

- 已发布内容不可 `UPDATE answer=...`；管理端编辑实际执行“复制为下一版本草稿”；
- 停用先更新事实源，使候选回源立即拒绝，再异步删除索引；
- `valid_to` 到期由查询过滤和回源校验双重执行，不依赖定时任务是否准时；
- 紧急下线提供 denylist/kill switch，可按知识 ID、版本 ID、租户或全局关闭自动回复；
- 审核人与创建人原则上分离；高风险知识必须双人审核。

## 7. 导入、清洗与索引流水线

### 7.1 导入流程

```text
上传 → 文件安全校验 → 解析 → 临时区 → 规范化 → 字段校验
    → 精确重复 → 近似重复/冲突 → 预览 → 人工确认
    → 草稿版本 → 审核 → Outbox → 索引 → 校验 → 发布
```

强制限制：

- 根据文件 magic bytes 校验类型，不能只相信扩展名；
- 限制文件大小、解压后大小、压缩比、总行数、单元格长度和文档页数；
- 禁止执行宏、脚本、外部链接和公式；
- 导入批次有唯一 `batch_id` 和文件 checksum，同一批次提交幂等；
- 每一行必须记录成功、跳过、冲突或失败原因；
- 自动分类只能产生“建议”，不得默认把不确定内容直接发布为公共知识；
- 人工创建、导入创建、知识缺口转知识必须复用同一个 validator 和 lifecycle；
- 重复检测至少使用 `tenant + scope + normalized_hash`，近似重复进入人工合并；
- 冲突知识不能同时激活，除非有效期或适用范围明确不重叠。

### 7.2 规范化

`normalizer.js` 输出结构化结果，而不是只返回一个字符串：

```js
{
  originalText,
  normalizedText,
  normalizedHash,
  scriptNormalizedText, // 简繁统一后的检索文本
  tokens,
  entities: [{ type, value, normalizedValue }],
  timeExpressions,
  piiFlags,
  normalizerVersion: 'kb-normalizer-1'
}
```

建议处理：Unicode NFKC、全半角、不可见字符、大小写、简繁映射、中文数字、常见时间表达、平台别称、受控同义词。手机号、证件号等不应进入长期检索日志明文。

同义词规则必须版本化并可测试。禁止把“社区活动”这类宽泛词设置为足以直接自动回复的强命中条件。

### 7.3 embedding 与索引版本

索引文档必须包含：

- `tenant_id/environment/platform/account/message_type`；
- `knowledge_id/version_id/chunk_id`；
- `risk_level/knowledge_type/review_status`；
- `valid_from/valid_to/serving_state`；
- `question/utterances/title/content/keywords`；
- `content_checksum/normalizer_version/embedding_version/index_generation`。

更换 embedding 模型时新建 generation，批量回填并离线评测，不覆盖旧向量。通过别名或配置原子切换；出现质量问题可立即切回旧 generation。

## 8. 在线查询与混合检索

### 8.1 查询上下文

检索输入不应只有 `message.content`。`query-builder.js` 接收：

```js
{
  tenantId,
  environment: 'PROD',
  platformCode,
  accountId,
  messageType,
  userMessage,
  postTitle,
  postBodySummary,
  parentComment,
  recentConversation,
  locale,
  now
}
```

约束：

- 上下文只取受限窗口并标注来源；
- 帖子正文、用户昵称、历史消息均视为不可信输入；
- 不把用户文本中的“忽略规则”“调用某工具”等内容当系统指令；
- 对代词、省略问句可使用上下文补全，但自动回复前必须保留原问题和补全依据；
- 缺少必要账号、地区、时间等槽位时输出 `CLARIFY`，不自行假设。

### 8.2 多意图识别

先用规则和轻量模型拆分并行意图，例如：

```text
“近期有什么活动，收费吗？”
→ intent_1: 查询近期活动
→ intent_2: 查询活动费用
```

只有每个必须意图都有兼容证据，且证据之间不冲突，才允许合并自动回复。否则：

- 可一次澄清的问题 → `CLARIFY`；
- 涉及实时数据/资格/风险 → `MANUAL_REQUIRED` 或调用受控业务动作；
- 确实无知识 → `KNOWLEDGE_GAP`。

### 8.3 并行召回

1. **精确召回**：`normalized_hash` 匹配标准问题和审核过的 utterance；
2. **词法召回**：标题、问题、别名高权重，关键词次之，答案/正文较低权重；
3. **向量召回**：解决同义表达和简繁表达，不能绕过范围过滤；
4. **结构化召回**：实体、分类、知识类型、时间范围；
5. **动态动作匹配**：只返回动作定义，实际结果来自业务服务。

所有召回请求都必须把 tenant、PROD、平台/账号、消息类型、审核、有效期、serving state 作为后端过滤条件。候选回到应用后再次按事实源校验，形成纵深防御。

推荐初始召回规模：每路 Top20～50，融合后 Top20，重排后保留 Top5～10。具体数值通过黄金集和压测确定，不直接把当前 Top3 固化为长期参数。

### 8.4 融合与去重

首期使用 Reciprocal Rank Fusion（RRF），降低不同检索器分数不可比造成的风险：

```text
RRF(d) = Σ 1 / (k + rank_r(d))
```

- 按 `knowledge_id + version_id` 去重；
- 同一知识多个 chunk 先做父文档聚合，避免一个文档占满候选；
- 精确别名可以增加受控 bonus，但仍必须通过范围、风险、有效期和冲突门禁；
- 不直接对 BM25 分数和 cosine 分数做未经校准的加权相加。

### 8.5 重排特征

重排器至少考虑：

- 问题/别名相关性；
- 意图是否一致；
- 实体、时间、地域和动作词是否一致；
- scope 具体度；
- 当前有效性与内容新鲜度；
- 来源权威性和审核级别；
- 是否完整覆盖问题中的必需槽位；
- 候选间是否相互冲突；
- 训练/评测数据中的历史正确率。

首期可使用确定性特征重排；引入模型 reranker 时必须固定版本、超时降级并经过离线评测。reranker 超时不得退化为“无门禁自动回复”，而是使用更严格的确定性路径或进入人工。

## 9. 置信度、冲突与最终决策

### 9.1 统一返回契约

```js
{
  decision: 'AUTO_REPLY' | 'CLARIFY' | 'MANUAL_REQUIRED' | 'KNOWLEDGE_GAP',
  confidence: 0.0,
  margin: 0.0,
  intents: [
    { id, name, requiredSlots, missingSlots, covered: true }
  ],
  candidates: [
    {
      knowledgeId,
      versionId,
      score,
      rank,
      retrievalSources,
      scopeSpecificity,
      riskLevel,
      rejectedReasons
    }
  ],
  evidences: [
    { knowledgeId, versionId, chunkId, text, sourceRef, checksum }
  ],
  reason: '...',
  policyVersion: 'kb-decision-1',
  indexGeneration: '...',
  retrievalTraceId: '...'
}
```

### 9.2 自动回复硬门禁

任一条件不满足，均不得 `AUTO_REPLY`：

- tenant、environment、platform、account、message type 范围完全匹配；
- 候选版本是事实源当前 `active_version_id`；
- 版本已审核、索引 `READY`、checksum 一致且当前有效；
- 来源不是 `SYSTEM_TEST`，也不在 denylist；
- 所有必需意图和槽位都有证据；
- Top1 与 Top2 不存在低间隔歧义；
- 候选证据之间不存在价格、时间、资格、地址等事实冲突；
- 风险级别允许自动回复；
- 置信度达到该知识类型、平台和风险级别对应阈值；
- 生成后的每个事实都能映射到 evidence，且通过平台长度和敏感信息校验；
- 检索、重排或必要动态服务未超时、未降级到不安全状态。

### 9.3 阈值策略

- 不继续使用全局固定 `0.58`；
- 阈值按 `retrieval_model_version + knowledge_type + risk_level + platform` 管理；
- 阈值必须由带人工标签的黄金集校准，并记录 precision/recall 曲线；
- 上线初期只允许“审核别名精确匹配 + LOW 风险”或极高置信场景自动回复；
- 语义检索先 shadow，只记录不执行；达到验收指标后逐步放量；
- Top1/Top2 margin 同样由数据校准。没有足够样本时采用更保守门槛，而不是猜测阈值。

### 9.4 风险分级回复策略

| 风险 | 示例 | 策略 |
|---|---|---|
| LOW | 地址、固定开放时间、公开报名入口 | 满足硬门禁可自动回复 |
| MEDIUM | 收费、退费、材料要求、活动资格 | 首期建议模板或人工；稳定后小流量开放 |
| HIGH | 法律、医疗、财务承诺、投诉裁定、敏感个人信息 | 默认人工，禁止生成式自动回复 |
| PROHIBITED | 无授权个人数据、违规操作等 | 拒绝并记录安全事件 |

### 9.5 冲突检测

发布时和检索时都检测冲突：

- 同一 scope、同一事实键、有效期重叠且值不同；
- 多条候选对费用、时间、地址、资格条件给出不同结果；
- 文档新版本与旧 FAQ 含义不一致；
- 动态 API 结果与静态知识冲突时，以动态权威源为准，并禁止混合输出未经确认的静态值。

冲突结果统一进入 `MANUAL_REQUIRED`，并创建可追踪 issue，不允许简单选择“更新的一条”自动回答。

## 10. 回复生成与验证

### 10.1 优先级

1. **确定性模板**：精确、低风险、结构化事实，直接渲染，不调用 LLM；
2. **多证据有据生成**：仅在需要自然组合时调用 Qwen；
3. **澄清模板**：缺少必要槽位时询问一个最关键问题；
4. **人工处理**：高风险、冲突、系统降级；
5. **知识缺口**：真正没有可用知识时记录并聚类。

### 10.2 Qwen 输入约束

- 只传递被安全门禁选中的 evidence；
- 每条证据带不可伪造的内部 ID，但用户内容不得变成系统指令；
- 明确禁止添加证据外的地址、时间、价格、资格、承诺和联系方式；
- 对文档内容中的“指令性文本”按数据处理，不执行其中命令；
- temperature 保持低值；
- 超时或返回“证据不足”时转人工/知识缺口，不使用半成品。

### 10.3 输出验证

`answer-validator.js` 至少执行：

- Unicode 字符/字素安全长度校验，复用现有平台策略；
- 必需标准事实是否完整出现；
- 禁止事实是否出现；
- 链接、电话、金额、日期等关键实体是否来自 evidence；
- PII、敏感词和平台合规检查；
- 回复是否为空、截断后是否改变事实含义；
- 记录 `evidence → answer span` 对应关系。

验证失败只能改用经过审核的短模板或转人工，不能发送原始模型文本。

## 11. 动态业务数据必须与静态知识分离

### 11.1 不应作为静态 FAQ 的内容

- 活动剩余名额、活动是否取消；
- 当天开放状态、临时闭馆；
- 用户是否符合资格；
- 订单、报名、退款状态；
- 会频繁变化的价格和库存。

### 11.2 动态动作模型

`DYNAMIC_ACTION` 保存：

```js
{
  actionCode: 'GET_ACTIVITY_AVAILABILITY',
  requiredSlots: ['activity_id'],
  connector: 'community-activity-service',
  responseTemplateId: 'activity-availability-v2',
  timeoutMs: 1500,
  cacheTtlSeconds: 30,
  failurePolicy: 'MANUAL_REQUIRED'
}
```

执行结果必须包含来源、获取时间、有效期和 request ID。API 超时、返回格式异常或数据过期时，不允许用旧 FAQ 猜测。

## 12. 一致性、幂等、重试和回滚

### 12.1 Transactional Outbox

在创建版本/审核/停用的同一个数据库事务中写入 outbox，worker 采用至少一次投递：

- `event_id` 全局唯一；
- 索引文档 ID 使用 `tenant:version:chunk:indexGeneration`；
- 重复消费覆盖同一文档，不生成重复版本；
- 指数退避 + 抖动；
- 达到最大重试后进入 dead-letter，并触发告警；
- 管理端显示索引失败原因并允许安全重试。

### 12.2 搜索时双重一致性检查

候选命中后按批量查询回源校验：

```text
candidate.version_id == knowledge_items.active_version_id
AND review_status == APPROVED
AND index_status == READY
AND valid_from <= now < valid_to（或 valid_to 为空）
AND checksum == index checksum
AND scope matches request
AND environment == PROD
AND source_type != SYSTEM_TEST
```

任何不一致候选直接剔除并计数告警。剔除后候选不足则 fail closed。

### 12.3 索引 generation 与回滚

- 索引 schema、normalizer、embedding 或 analyzer 变化时新建 generation；
- 新旧 generation 并存，使用配置/别名按租户灰度；
- 切换前验证文档数量、抽样 checksum、黄金集指标和权限过滤；
- 回滚只切回旧 generation 和旧 decision policy，不回写或破坏事实源；
- 发布错误可把 `active_version_id` 原子指回上一已审核 READY 版本，再异步同步索引；
- 紧急情况下全局关闭 `AUTO_REPLY`，检索仍可为人工提供候选。

## 13. API 契约建议

### 13.1 管理 API

- `POST /api/knowledge/items`：创建稳定知识与首个草稿；
- `POST /api/knowledge/:id/versions`：基于已发布版本创建新草稿；
- `POST /api/knowledge/versions/:versionId/submit-review`；
- `POST /api/knowledge/versions/:versionId/approve`；
- `POST /api/knowledge/versions/:versionId/publish`：只创建索引任务，返回 `202`；
- `POST /api/knowledge/:id/disable`；
- `GET /api/knowledge/:id/history`：版本、审核和发布历史；
- `GET /api/knowledge/index-jobs/:jobId`；
- `POST /api/knowledge/imports/preview`；
- `POST /api/knowledge/imports/:batchId/commit`：幂等提交。

所有写 API 必须支持：认证、角色权限、CSRF/来源保护（如适用）、`Idempotency-Key`、乐观锁 `expectedRevision`、结构化错误码和审计日志。

### 13.2 内部检索 API

```js
POST /internal/knowledge/retrieve
{
  tenantId,
  environment,
  platformCode,
  accountId,
  messageType,
  messageId,
  query,
  context
}
```

返回第 9.1 节契约。业务消息处理只消费 `decision` 和已验证 `evidences`，不得自行读取候选 Top1 后绕过决策引擎。

### 13.3 错误码

建议至少包括：

- `KB_SCOPE_MISMATCH`
- `KB_NO_EVIDENCE`
- `KB_LOW_CONFIDENCE`
- `KB_LOW_MARGIN`
- `KB_MULTI_INTENT_INCOMPLETE`
- `KB_EVIDENCE_CONFLICT`
- `KB_VERSION_MISMATCH`
- `KB_INDEX_NOT_READY`
- `KB_EXPIRED`
- `KB_HIGH_RISK`
- `KB_DYNAMIC_SOURCE_UNAVAILABLE`
- `KB_ANSWER_VALIDATION_FAILED`

错误码进入检索日志和指标，外部用户只看到合适的澄清或人工提示。

## 14. 可观测性、评测与运营闭环

### 14.1 每次检索必须记录

- `retrievalTraceId/messageId/tenant/platform/account/messageType`；
- 原始问题的脱敏摘要和 normalized hash；
- normalizer、索引 generation、embedding、reranker、decision policy 版本；
- 每路召回耗时、候选 ID、原始 rank、融合分、重排分；
- 被剔除原因、最终证据、confidence、margin、decision；
- Qwen 模型版本、耗时、token 和输出验证结果；
- 人工最终判定和用户反馈。

### 14.2 核心指标

质量指标：

- Auto Reply Precision（自动回复正确率）；
- Answerable Recall@K；
- 无答案问题正确拒绝率；
- 多意图完整覆盖率；
- 冲突阻断率；
- 知识缺口聚类命中率；
- 人工改写率和撤回率。

安全指标：

- 跨 tenant/platform/account 泄漏次数；
- 未审核、过期、测试知识命中次数；
- 版本/checksum 不一致次数；
- 高风险自动回复次数；
- 输出验证失败后仍发送次数。

性能指标：

- p50/p95/p99 检索延迟；
- 各召回器超时率；
- Outbox 堆积和最大延迟；
- 索引失败/重试/dead-letter 数；
- 索引文档数与事实源 READY 版本数差异。

### 14.3 黄金集

从真实消息脱敏抽样，建立至少以下标签：

- 可回答/不可回答；
- 标准 knowledge/version；
- 意图和必要槽位；
- 风险级别；
- 期望 decision；
- 禁止出现的错误事实。

每次改动 normalizer、索引、embedding、reranker、阈值或 prompt 都必须运行同一黄金集，并与当前生产基线比较。线上错误必须固化为回归用例。

## 15. 故障与威胁分析

| 风险 | 防护 | 失败动作 |
|---|---|---|
| 跨平台/账号知识泄漏 | 后端 metadata filter + 回源二次校验 + 隔离测试 | 立即关闭自动回复并告警 |
| 测试知识混入生产 | environment/source 双过滤，发布约束 | 候选剔除，记录安全事件 |
| 索引旧版命中 | active_version/checksum 校验 | 剔除；无候选则人工 |
| 发布成功但索引失败 | APPROVED 与 PUBLISHED 分离，INDEXING 状态 | 旧版继续服务 |
| 停用后索引残留 | 事实源先停用，候选回源校验 | 残留结果不可用 |
| 模糊问题高分错配 | 多路召回、重排、margin、多意图门禁 | 澄清或人工 |
| 用户 prompt injection | 用户内容始终作为不可信数据 | 忽略指令，不执行工具 |
| 知识文档投毒 | 来源权限、审核、内容扫描、审计 | 拒绝发布 |
| 导入压缩炸弹/超大文件 | 大小、压缩比、页数和超时限制 | 拒绝解析 |
| LLM 幻觉 | 证据限定 + 实体核对 + 输出验证 | 丢弃模型输出 |
| 动态数据过期 | TTL、时间戳、权威 API | 人工或稍后再试 |
| 搜索服务不可用 | 超时、熔断、可选精确缓存 | 仅安全精确模板或人工 |
| 日志泄露 PII | 脱敏、hash、分级权限、保留期 | 阻断记录并告警 |
| 管理员误发布 | 双人审核、预览、乐观锁、回滚 | 恢复上一版本 |

## 16. 从当前系统迁移的分阶段方案

### 阶段 0：建立质量基线与立即止血（不改变基础设施）

目标：先阻止已知高风险路径。

1. 为当前检索建立固定回归集，包含已发现的报名、简繁、多意图错误；
2. 生产检索显式排除 `source='SYSTEM_TEST'`；
3. 所有创建和知识缺口发布统一走答案长度、重复、分类和范围校验；
4. 禁止已发布行原地编辑；
5. 增加 Top1/Top2 margin 和多意图保守门禁；
6. 记录 Top3/Top10 候选与决定原因；
7. 增加全局 `AUTO_REPLY_KILL_SWITCH`。

回滚：保留现有检索入口和数据库备份，新增门禁均用 feature flag 控制；回滚只能降低自动化程度，不能重新允许测试知识。

### 阶段 1：新数据模型 + SQLite FTS5 + Outbox

目标：在单机部署中完成正确性基础。

1. 新建 item/version/scope/utterance/review/outbox/log 表；
2. 从当前 `knowledge` 表 backfill，原 ID 保存到 `legacy_id`；
3. 对每条数据生成 checksum、scope 和环境，`SYSTEM_TEST` 进入 TEST；
4. 创建 SQLite FTS5 索引和 index worker；
5. 旧写入口改为调用 lifecycle，旧 `knowledge.js` 成为适配器；
6. 新检索以 shadow 模式运行，与旧结果对比，不发送新结果；
7. 完成数据总数、checksum、范围和随机抽样验收。

### 阶段 2：混合检索与安全决策灰度

目标：解决同义表达、歧义和多意图。

1. 接入 utterance、词法召回、向量召回、RRF 和确定性重排；
2. 建立黄金集并校准不同风险阈值；
3. 先只对 LOW 风险和审核别名精确命中启用；
4. 按 1% → 5% → 20% → 50% → 100% 灰度；
5. 每一阶段比较自动回复正确率、人工改写率和知识缺口变化；
6. 任一安全硬指标失败立即退回 shadow。

### 阶段 3：PostgreSQL / OpenSearch 生产化

触发条件：单机并发、数据量、日志量或高可用要求超过 SQLite 能力，而不是仅凭条目数机械迁移。

1. PostgreSQL 接管事实源和 Outbox；
2. OpenSearch 或 PostgreSQL + pgvector 接管大规模检索；
3. 使用 generation 全量重建并校验；
4. 双读对比，不做无事务保障的数据库双写；
5. 灰度切换检索流量，旧 SQLite 保持只读回滚窗口；
6. 完成备份恢复、故障转移、容量和压测后再下线旧链路。

### 阶段 4：运营闭环和持续优化

- 知识缺口自动聚类但人工发布；
- 从高质量人工回复生成 utterance 建议；
- 建立变更影响分析：发布前显示会影响的历史问题；
- 定期识别过期、低使用、互相冲突知识；
- 逐步引入模型 reranker，但保持可回滚和确定性门禁。

## 17. 测试矩阵

### 17.1 单元测试

- Unicode、简繁、全半角、符号、数字、时间和同义词规范化；
- scope 组合和具体度排序；
- 生命周期非法状态转换；
- checksum、幂等 key、重复和冲突检测；
- RRF、去重、margin、多意图覆盖；
- 答案长度、实体来源和敏感信息验证；
- 过期边界：`valid_from <= now < valid_to`。

### 17.2 属性/模糊测试

- 任意 tenant/platform/account 组合不得返回范围外版本；
- 任意 Unicode/空字符串/超长字符串不崩溃；
- 重复消费同一 Outbox 事件结果一致；
- 任意候选顺序变化不改变硬门禁结果；
- 关闭/过期/回滚后旧版本永远不能被接受。

### 17.3 集成测试

- 发布成功、索引失败、重试成功、死信；
- 索引已写但事实源未激活；
- 事实源已切换但索引可见性延迟；
- 搜索服务、embedding、reranker、Qwen 超时；
- 多 worker 并发消费和重复事件；
- 版本回滚、generation 切换、tombstone 清理；
- 导入中断、重复提交、恶意压缩文件和超长内容。

### 17.4 回归样例

必须永久保留：

1. “我想参加社区活动，怎样报名？”应匹配报名知识，而不是近期活动介绍；
2. “内地支付宝怎么绑定银行卡？”能匹配繁体表达的正确知识；
3. “近期有什么活动，收费吗？”必须识别两个意图，证据不全不得只回答一个；
4. 微博专属知识不得出现在其他平台；
5. `SYSTEM_TEST` 在生产请求中始终不可见；
6. 已停用、过期、索引 checksum 不一致的知识不得自动回复；
7. Top1/Top2 高度接近且语义不同必须澄清或人工；
8. 高风险知识即使精确命中也不得走生成式自动回复。

### 17.5 容量与性能测试

分别生成 1 万、10 万、100 万知识/分块数据集，验证：

- 检索延迟不会随知识总数线性增长；
- tenant/platform filter 后的结果完整且无泄漏；
- 索引重建期间旧 generation 持续可用；
- 日志写入不阻塞主回复链路；
- Outbox 积压恢复后不产生重复索引或错误激活。

## 18. 上线硬验收标准

以下属于**必须为零或 100% 通过的安全门槛**：

1. 跨 tenant、platform、account、environment 泄漏：**0**；
2. 未审核、已停用、已过期、`SYSTEM_TEST` 知识参与生产自动回复：**0**；
3. 索引版本/checksum 不一致仍自动回复：**0**；
4. 发布索引失败时新版本被搜索接受：**0**；
5. 高风险内容未经规定人工流程自动发送：**0**；
6. 输出验证失败后仍发送模型原文：**0**；
7. 已发布版本被原地修改：**0**；
8. 生命周期、隔离、迁移、回滚测试：**100% 通过**。

以下属于首轮建议质量 SLO，需以真实黄金集校准后冻结：

- LOW 风险自动回复 Precision ≥ **99.5%**；
- 可回答问题 Recall@10 ≥ **95%**；
- 不可回答问题正确拒绝率 ≥ **98%**；
- 多意图完整覆盖率 ≥ **98%**；
- p95 检索延迟：本地 FTS 阶段 ≤ **300ms**，独立搜索服务阶段 ≤ **200ms**（不含 Qwen）；
- 索引任务成功率 ≥ **99.9%**，失败事件必须可重试且有告警。

若黄金集规模不足以证明指标，不得直接全量开启语义自动回复，应继续 shadow 或仅开放精确模板路径。

## 20. 最终建议

本项目应采用“**先把发布和检索变正确，再把召回变智能，最后把基础设施变大**”的顺序：

1. 第一阶段不要急于用向量数据库替换当前实现，先建立不可变版本、范围隔离、统一校验、Outbox、日志和 fail-closed 门禁；
2. 第二阶段用 FTS/精确别名解决大部分高确定性问题，同时让新混合检索 shadow 运行；
3. 第三阶段在黄金集证明质量后，逐步开放向量与重排结果参与自动回复；
4. 数据量和并发达到瓶颈后，再把事实源迁移到 PostgreSQL、搜索迁移到 OpenSearch/pgvector；
5. 无论使用何种模型和索引，最终自动回复必须经过相同的版本、范围、时效、冲突、风险和证据门禁。

该方案可以在保留现有 SQLite、管理页面和消息处理流程的前提下分阶段落地，不要求一次性大重写。其核心不是保证检索永远“猜对”，而是保证系统在无法证明答案可靠时**不会擅自回答**。
