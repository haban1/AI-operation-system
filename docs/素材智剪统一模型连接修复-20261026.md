# 素材智剪统一模型连接修复

日期：2026-10-26

## 原因

OpenChatCut 原本已使用天河统一模型网关，内部令牌与天河配置一致。实际请求经 `/llm/chat/completions` 转发时，携带了编辑器浏览器的 `Origin: http://127.0.0.1:5199`。天河先执行来源校验，返回 `403 CORS_ORIGIN_DENIED`；OpenChatCut 将所有 401/403 显示为“OpenAI 认证失败”，因此看起来像 Key 无效。

另外，设置页通过 `GET /models` 检查连接，天河此前没有该接口，会返回 404。

## 改动与配置

- Docker 构建时运行 `deploy/workbench/patch-openchatcut.mjs`，只在上游请求中移除 Origin、Referer 和浏览器 Fetch Metadata。编辑器入口的来源校验及天河令牌校验继续生效。
- 天河新增需要令牌认证的 `GET /api/model/v1/models`，返回已配置的模型用途别名。模拟模式和缺少 Key 时返回明确错误，不暴露真实 Key。
- 外部 OpenChatCut 源码仍固定在 `7fa4b7903e7ebecf832a36249f0c0c755200cc17`；适配脚本保存在本项目，重新构建可自动应用。
- 新镜像：`tianhe-openchatcut:7fa4b79-tianhe1`。

素材智剪 Agent 继续使用以下配置，无需单独申请或填写 OpenAI Key：

| 配置 | 值 |
| --- | --- |
| 协议 | OpenAI 兼容 Chat Completions |
| API URL | `http://web:3100/api/model/v1` |
| 模型 | `tianhe-workbench-chat` |
| 鉴权 | 本地已有的天河内部令牌，由服务端使用 |
| 实际服务商 Key、模型、地址 | 动态读取天河主程序 AI 配置 |

验证时实际模型为 `deepseek-flash`。以后在天河修改主模型或服务商 Key，下一次调用即使用新配置。此处统一的是 Agent 文本模型；界面中的图像、视频、转写等独立服务仍按其自身能力配置。

## 验证结果

- `node --test test/model-gateway.test.js`：6 项通过。
- 镜像构建执行新增代理回归测试及 OpenChatCut 原有 `server/llm-proxy.verify.ts`：通过。
- 代理回归覆盖普通 JSON、SSE 流式传输、浏览器来源隔离、错误令牌被拒绝。
- 实际设置连接测试：HTTP 200，鉴权通过，可读取模型列表。
- 实际 `/llm/chat/completions`：普通和流式调用均 HTTP 200，模型返回“连接成功”。
- 智慧驱动嵌入页面中创建临时工程验证：Agent 正常显示“连接成功”。
- OpenChatCut 与天河 Web 容器均 healthy，工作台 3 条线路全部在线。

部署只重建 OpenChatCut，并重建天河 Web 容器以加载新接口、重新挂载 OpenChatCut SQLite WAL 文件。原有工程、素材和模型设置保留。

## 重新部署

在项目根目录执行：

```powershell
docker compose -f compose.yaml -f compose.wechat.yaml -f compose.workbench.yaml build openchatcut
docker compose -f compose.yaml -f compose.wechat.yaml -f compose.workbench.yaml up -d --no-deps --wait openchatcut
# 待 OpenChatCut 数据库及 -wal/-shm 文件就绪后，刷新 Web 的只读文件挂载。
docker compose -f compose.yaml -f compose.wechat.yaml -f compose.workbench.yaml up -d --force-recreate --no-deps --wait web
```
