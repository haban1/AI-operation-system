# 微信原生客服迁移与开发说明（2026-10-19）

当前微信客服运行在 8080 机器人系统内。独立的 8000 Python Agent 和它的 PostgreSQL 已停止，默认 Compose 不再启动它们。天河工作空间的「微信客服」直接嵌入机器人后台。

## 运行链路

微信消息 → 原微信协议服务（server）→ 本项目 Go 机器人客户端（client）→ 原生 Agent → search_document 检索原生 Qdrant 知识库 → 原生 Agent 生成回答 → 机器人发回微信。

聊天和向量模型仍由天河统一模型网关提供。天河 RAG 服务仅为微信提供本地文本向量计算；微信知识的存储、分块、索引、检索、Agent 和回复逻辑由机器人负责，不再调用 8000，也不使用原来的“无法整理完整答复，返回检索原文”降级链路。

天河其他渠道的知识库和问答流程继续独立使用。此次迁移将已有 5 份已发布文档复制进机器人「客服业务知识」分类，形成 106 个原生分块；后续两边资料不会自动同步。微信的新资料在 8080「知识库」维护。

## 页面与使用

在天河工作空间打开「微信客服」，使用原机器人登录密钥登录，点击机器人的管理按钮：

- 人工接待：选择通知好友、默认问答知识库；查看接待队列、主动接管、恢复 AI。实际聊天在微信客户端进行。客户明确请求人工时，原生 Agent 调用接待工具；客服通过微信主动回复私聊也会暂停该会话的 AI。
- 好友群发：选择好友、文字或图片，预览并确认，查看逐人结果。最多 500 人、文字 2000 字、图片 10 MB，逐个发送。请求编号防重复；发送中断的任务标记为“结果待核对”，不会自动重发。更换浏览器或清除本地存储后，仍应先核对任务历史。
- 知识库：使用原生文本知识分类和文档管理。私聊使用「人工接待」里的默认知识库；群聊优先使用自身绑定，未绑定时使用默认知识库。

接待状态存入机器人自己的 MySQL。接管后，生成中的旧回答和旧工具调用都会失效；恢复 AI 只处理后续新消息。接待通知发送失败不会取消接管，会在队列里提示失败。群聊按“群 + 发言人”分别记录接待状态。

2026-10-20 微信 AI 回复改为纯文本格式：聊天提示词要求自然段或数字编号，发送前清理加粗、斜体、标题和星号列表等常见 Markdown 标记。覆盖私聊、群聊及工具返回的文本/长文本；保留脱敏号码、公式、网址和代码里的有效星号。人工编写的群发内容不经过此清理。修改位于 wechat-robot-client，重建并更新 robot-client 后生效，历史消息不会修改。格式与私聊/群聊发送路径均有模拟测试，不向真实微信发送测试消息。

2026-10-20 已修复局域网登录页的 HTTPS 提示：原生构建脚本读取 compose.wechat.yaml 中的 WECHAT_ROBOT_ADMIN_URL，并将这个完整 HTTP origin（协议、主机、端口）写入前端 PUBLIC_ROBOT_HTTP_ORIGIN。当前允许 http://10.70.72.78:8080；其他 HTTP 地址仍提示使用 HTTPS。更换后台地址后需重新构建并更新 robot-ui。使用 scripts/verify-robot-login.cjs 验证登录页，添加 --live 可检查真实后台登录和刷新后的会话；测试不发送微信消息。

内嵌登录要求天河与机器人使用相同站点。当前两者发布在同一台主机，compose.wechat.yaml 启用 WECHAT_ROBOT_ADMIN_FOLLOW_HOST=true：从 127.0.0.1、localhost 或局域网 IP 打开天河，内嵌后台和“独立窗口打开”均使用相同主机的 8080 端口，避免跨站 Cookie 导致登录后又回到登录页。地址的协议、端口、路径仍来自 WECHAT_ROBOT_ADMIN_URL；此选项默认关闭，机器人部署到其他主机时应关闭。若改用 HTTPS，两个入口都须配置对应 HTTPS 地址。修改该 Compose 环境变量后用 up -d --no-deps web 重建 Web 容器，单纯 restart 不会更新环境变量。scripts/verify-wechat-login.cjs 验证三个入口的真实内嵌登录、重新加载、整页刷新、切换工作空间和独立窗口会话，禁止微信发送请求。

当前保留 4 位好友、2 条旧接待关联记录（迁移时没有活动中的接待）、原接待通知配置。旧系统没有群发记录。机器人旧日志显示 2026-10-17 已掉线；需在 8080 重新扫码后才能实际收发消息。

2026-10-20 后续检查确认微信已在线。已准备群早报、群总结和欢迎语模板，用户以后自行选群；朋友圈自动点赞已开启，自动评论关闭。配置、选择群的方法及视觉接口限制见 [微信群运营与朋友圈-20261020.md](微信群运营与朋友圈-20261020.md)。

## 模型配置

继续在天河「系统设置 → 企微及 AI」设置接口、密钥、对话模型、视觉模型。

机器人中保留内部连接：http://tianhe-model-gateway:3100/api/model/v1，聊天模型 tianhe-robot-chat，向量模型 tianhe-robot-embedding，向量维度 512。实际向量模型在天河设为 local:BAAI/bge-small-zh-v1.5，使用本地模型；DeepSeek 的聊天接口不提供此向量模型。

切换向量模型或维度必须重建对应原生索引。此次仅重建了确认点数为 0 的 knowledge、memories 集合，原 schema 已备份。已配置后台 HTTP 登录；以后接入 HTTPS 时可为 robot-admin 设置 SESSION_COOKIE_SECURE=true。

以下命令在 project 目录执行。仍依赖原有 wechat-robot 网络上的协议服务、MySQL、Redis、Qdrant 和 nginx；不要删除这些服务及数据卷。

```powershell
# 启动天河及模型网关
docker compose -f compose.yaml -f compose.wechat.yaml up -d --build --wait --wait-timeout 240

# 机器人源码修改后构建三个镜像（Docker 内使用 Go、pnpm 8.15.9）
./scripts/build-robot-native.ps1
docker compose --env-file .env.robot-native -f compose.robot.yaml up -d
docker exec wechat-nginx nginx -s reload

# 只重启天河挂载的源码
docker compose -f compose.yaml -f compose.wechat.yaml restart web rag
```

.env.robot-client、.env.robot-admin 保存原部署连接信息；.env.robot-native 保存机器人编号和 Skills 目录。这些文件及 backups 含本机凭据，均被 Git 忽略。后台重建机器人客户端时使用 WECHAT_ROBOT_CLIENT_IMAGE=tianhe-wechat-client:native，避免丢失新增功能。不要用原部署 Compose 覆盖这三个自定义容器。

## 迁移记录与回退

本次完整备份：backups/robot-native-20261019-180005。包括原容器配置、MySQL 导出、PostgreSQL 归档、原生设置、接待数据、已发布知识、空向量集合 schema。旧三个容器以 -before-native 后缀保留，已停止并关闭自动重启；旧 8000 和数据库同样停止。不要同时启动旧新回复引擎。

scripts/migrate-robot-native.py 提供 cutover、import、verify、enable 阶段；用于已准备好本机备份和环境文件的升级，不是新机器初始化工具。阶段会保留原设置、停旧服务、迁入资料并验证后开启新回复。已经完成的 cutover 不应再次执行。

需要回退时：先停原生客户端并备份迁移后的 MySQL/Qdrant；移除本次 compose.robot.yaml 的三个容器（不删卷），把三个 -before-native 容器恢复原名。启动旧 PostgreSQL，恢复 native-cutover.json 中 global_settings、system_settings 后再启动旧 8000，恢复旧 Compose 配置并重建 Web，最后重载 nginx。原生新增表和知识可保留，旧 Python Agent 不使用这些表。恢复之前先核对迁移后是否产生新接待/群发记录，避免丢失新业务数据。
