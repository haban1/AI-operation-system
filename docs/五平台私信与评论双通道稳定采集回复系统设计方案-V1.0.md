## 1. 文档目的

本方案用于解决当前私信和评论链路中的五类核心问题：

1. 私信依赖未读红点，人工或其他设备提前打开后可能漏采；
2. 私信和评论共用页面或任务时，需要来回跳转，容易互相阻塞和干扰；
3. AI 生成回复期间，用户继续发送新消息，旧回复可能过时或新消息可能漏采；
4. 私信列表会因其他用户发消息而重新排序，不能依赖列表位置重新寻找目标用户；
5. 多用户、多平台并发时，需要保证不串上下文、不发错目标、不重复发送、不静默漏消息。

本方案的核心目标不是承诺平台、网络和浏览器永远不发生异常，而是保证：

> 每条平台消息要么在同步时限内进入 Web 和处理链路，要么明确显示“同步不完整、正在重试或需要人工确认”；任何异常都不能伪装成“暂无消息”或“回复成功”。

## 2. 当前实现核对结论

本节只说明当前源码真实存在的能力和缺口，不把目标设计写成已实现功能。

### 2.1 当前支持平台

`agent/rpa-adapters/registry.js` 当前注册：

- `douyin`：抖音；
- `xiaohongshu`：小红书；
- `wechat_channels`：微信视频号；
- `bilibili`：B站；
- `weibo`：微博。

### 2.2 当前已经具备的基础

当前项目已经有以下可复用能力：

1. `agent_jobs` 持久化任务表，支持排队、领取、租约、恢复、幂等键和人工确认状态；
2. `conversations` 会话表，支持会话版本、最近来消息和多用户会话隔离；
3. `withConversationSerial()`，可以让同一个会话串行处理；
4. `isMessageConversationCurrent()`，可以让新消息到达后使旧回复任务失效；
5. 知识库检索、多问题拆分、上下文追问、确认/否认、转人工和回复安全校验；
6. 平台回复目标唯一性校验、发送后回显或回执校验；
7. SQLite 已启用 WAL 和 busy timeout，具备继续增强并发写入的基础。

### 2.3 当前确认的私信采集缺口

`agent/rpa-adapters/assisted-platform.js` 当前私信列表主筛选包含：

```js
item.unread && item.userName
```

因此当前主链路更接近：

```text
有未读红点并识别到用户名
→ 才进入会话检查
```

这会造成：

```text
用户发来消息
→ 手机端、人工或其他设备提前打开
→ 红点消失
→ RPA 扫描时跳过
→ 数据库没有消息
→ Web 显示暂无私信
```

当前抖音已读会话恢复逻辑又主要查找“最后一条账号发出消息之后的来消息”。如果最后一条是账号回复，之前缺失的用户消息可能仍不会被补录。

### 2.4 当前回复目标定位的安全与不足

当前公共适配器已经采用以下保护：

```text
用户名和列表预览匹配
→ 要求目标唯一
→ 点击会话
→ 核对会话标题
→ 检查原消息
→ 检查 conversationId、messageId 和消息方向
```

匹配不清楚时倾向停止发送，而不是猜测目标，这一安全原则必须保留。

当前不足是：前半段仍较依赖“用户名 + 当前列表预览”。列表预览改变、会话被顶出当前加载范围、同名用户或页面延迟时，可能找不到目标。目标设计必须改成“稳定会话 ID 优先定位，昵称和预览只作为辅助证据”。

### 2.5 当前任务调度不足

`src/server.js` 当前任务领取顺序主要是：

```text
REPLY
→ DETECT_MANUAL_REPLY
→ COLLECT_MESSAGES
→ 其他任务
```

同类型任务主要按任务 ID 先后领取。当前没有完整区分：

- 私信采集与评论采集；
- 私信回复与评论回复；
- 平台、账号和业务通道；
- 同一会话消息聚合；
- 不同业务通道的独立页面锁；
- 采集任务不被回复积压饿死的保障。

## 3. 设计原则

### 3.1 五条不可破坏的稳定性原则

1. **红点只决定优先检查，不决定消息是否存在。**
2. **平台消息 ID 决定是否已同步，不能只通过消息文字判断。**
3. **是否保存消息与是否需要回复必须分开。**
4. **找人依赖稳定会话 ID，不能依赖列表位置或昵称。**
5. **平台结果不确定时停止自动重试，不能把不确定当成功或普通失败。**

### 3.2 失败关闭原则

以下任一条件不满足时禁止自动发送：

- 当前账号身份无法确认；
- 当前页面业务类型不正确；
- 当前会话 ID 与任务不一致；
- 原消息 ID 不存在或方向不是用户来消息；
- 同名目标不唯一；
- 发送前发现会话版本变化；
- 页面时间线不稳定；
- 已点击发送但没有可靠回执。

系统宁可进入 `NEEDS_CONFIRMATION`，也不能猜测发送。

### 3.3 双通道独立原则

私信和评论是两个独立业务通道：

```text
私信通道：独立采集、队列、页面、锁、检查点、回复和健康状态
评论通道：独立采集、队列、页面、锁、检查点、回复和健康状态
```

两条通道同时运行，不存在“私信处理完才能处理评论”的业务顺序。

如果底层存在共享资源限制，例如 AI 并发、账号发送频率或系统级鼠标焦点，应通过保留资源配额和限速解决，不能重新把两条通道合并成一个长串行任务。

## 4. 总体架构

```text
平台账号
│
├── PRIVATE_MESSAGE 私信通道
│   ├── 私信专用 Page / API 会话
│   ├── 私信增量采集器
│   ├── 私信历史核对器
│   ├── 私信事件入库
│   ├── 私信回复任务队列
│   ├── 私信上下文与知识库处理
│   └── 私信发送与回执验证
│
└── COMMENT 评论通道
    ├── 评论专用 Page / API 会话
    ├── 评论增量采集器
    ├── 评论历史核对器
    ├── 评论事件入库
    ├── 评论回复任务队列
    ├── 评论上下文与知识库处理
    └── 评论发送与回执验证
```

中央调度器只负责：

- 生成小任务；
- 领取任务；
- 控制并发；
- 维护租约；
- 失败重试；
- 记录状态和指标。

中央调度器不直接决定回复发给谁，平台适配器也不能自行生成业务答案。

## 5. 任务与队列设计

### 5.1 不要求引入外部消息中间件

按当前预估规模：

```text
5 个平台 ×（30 条私信 + 30 条评论）= 300 条/天
```

继续使用 SQLite 中的持久化任务表即可，不需要第一阶段引入 RabbitMQ 或 Kafka。

但要把当前 `agent_jobs` 从“通用任务列表”增强为按业务通道可调度的持久化队列。

### 5.2 建议任务类型

```text
COLLECT_PRIVATE_MESSAGES
RECONCILE_PRIVATE_MESSAGES
GENERATE_PRIVATE_REPLY
SEND_PRIVATE_REPLY
VERIFY_PRIVATE_REPLY

COLLECT_COMMENTS
RECONCILE_COMMENTS
GENERATE_COMMENT_REPLY
SEND_COMMENT_REPLY
VERIFY_COMMENT_REPLY
```

生成回复与实际发送分开后，AI 请求不会长期占用浏览器页面。

### 5.3 逻辑队列键

每个任务至少包含：

```text
platformCode
accountId
channelType
conversationId / commentId
sourceMessageIds
firstPendingAt
conversationVersion
idempotencyKey
```

逻辑通道键：

```text
{platformCode}:{accountId}:{channelType}
```

例如：

```text
douyin:2:PRIVATE_MESSAGE
douyin:2:COMMENT
bilibili:3:PRIVATE_MESSAGE
bilibili:3:COMMENT
```

### 5.4 队列顺序

私信和评论不互相比较顺序。

私信队列内部：

1. 已开始处理的同一会话补充消息合并到当前批次；
2. 其余会话按 `first_pending_at` 从早到晚处理；
3. 同一个会话一次只处理一个批次；
4. 一个会话完成一批后轮转到其他会话，防止单个高频用户长期独占。

评论队列内部：

1. 默认按评论事件时间从早到晚；
2. 同一原评论只能有一个有效回复任务；
3. 已回复、删除、无法唯一定位或不允许自动回复的评论不进入发送队列。

### 5.5 任务状态

统一状态建议：

```text
QUEUED
RUNNING
RETRYING
SUCCESS
CANCELLED
NEEDS_CONFIRMATION
MANUAL_REQUIRED
```

附加执行状态：

```text
NOT_ATTEMPTED
GENERATED
SEND_ATTEMPTED
SEND_CONFIRMED
SEND_REJECTED
SEND_UNCERTAIN
```

只要发生不可逆发送动作且没有可靠回执，必须进入：

```text
NEEDS_CONFIRMATION + SEND_UNCERTAIN
```

禁止自动重发。

## 7. 私信采集设计

### 7.1 双路径采集

#### 路径 A：未读快速通道

```text
发现红点
→ 立即打开会话
→ 读取稳定时间线
→ 保存新事件
```

红点只用于降低响应延迟。

#### 路径 B：最近活跃会话核对通道

```text
没有红点也定期检查最近活跃会话
→ 获取会话 ID 和消息 ID
→ 与数据库水位比较
→ 补录缺失事件
```

该路径用于处理：

- 人工或手机端提前读过；
- 会话打开时新消息自动变成已读；
- 服务停机后恢复；
- DOM 首次加载不完整；
- 列表预览被账号回复覆盖。

### 7.2 页面稳定判断

进入会话后不能读取一次就立即结束。必须对以下内容取得连续稳定快照：

- 会话标题；
- conversationId；
- 可见聊天气泡数量；
- 每个气泡的 messageId；
- 消息方向；
- 最后一条消息；
- 页面加载状态。

缺少标题、会话 ID、时间线方向或消息 ID 时，必须标记同步不完整并重试，不能报告“暂无私信”。

### 7.3 同步完整状态

统一输出：

```text
SYNC_COMPLETE_NO_NEW_EVENTS
SYNC_COMPLETE_WITH_EVENTS
SYNC_INCOMPLETE_RETRYING
SYNC_BLOCKED_LOGIN_REQUIRED
SYNC_NEEDS_CONFIRMATION
```

Web 只有在 `SYNC_COMPLETE_*` 时才允许显示“暂无新消息”。

### 7.4 历史补采不触发批量回复

历史核对发现旧消息时：

```text
保存和显示：是
进入上下文：是
自动回复：默认否
```

如果后面已存在账号发出的回复，应标记：

```text
reply_disposition = ALREADY_HANDLED
```

只有可靠确认是新来消息且尚未被覆盖时，才能进入回复队列。

## 8. 私信目标定位与列表重排

### 8.1 任务不得依赖列表位置

采集时必须保存：

```text
conversationId
platformUserId
conversationUrl（如果平台提供）
sourceMessageIds
sourceContent
conversationVersion
```

回复时定位优先级：

1. 通过固定会话 URL 直接打开；
2. 通过列表行中的 conversationId 定位；
3. 通过平台用户 ID 或会话搜索进入；
4. 分页或滚动最近会话，直到找到稳定 ID；
5. 仍无法定位则停止自动发送。

昵称和列表预览只能作为辅助证据，不能成为普通业务消息的唯一发送依据。

### 8.2 进入会话后的发送前校验

发送前必须确认：

```text
当前平台账号正确
当前页面是 PRIVATE_MESSAGE
当前 conversationId 与任务一致
任务中的 sourceMessageId 存在
sourceMessage 方向为 INCOMING
消息文本或摘要证据一致
时间线已稳定
消息尚未被后续账号回复覆盖
当前会话版本未变化
```

任一失败即禁止发送。

## 9. 用户回复过程中再次发消息

### 9.1 三次读取机制

私信回复至少执行三次时间线读取：

```text
进入会话后读取一次
AI 生成完成、发送前再读取一次
发送动作完成后再读取一次
```

### 9.2 会话版本机制

AI 开始生成时记录：

```text
conversationVersion = N
lastIncomingMessageId = M1
```

发送前如果变为：

```text
conversationVersion = N + 1
lastIncomingMessageId = M2
```

说明用户发来了补充消息。处理方式：

```text
取消旧草稿
→ 合并 M1 与 M2
→ 重新分析上下文和知识库
→ 重新生成完整回复
```

### 9.3 发送边界竞态

如果新消息在点击发送前被发现：

```text
旧回复不发送，合并重答
```

如果新消息在回复已经发出后到达：

```text
原回复只覆盖原批次
新消息进入下一批次
```

如果无法确认回复是否已经发出：

```text
进入 NEEDS_CONFIRMATION
先核对平台己方气泡或回执
禁止自动重发
```

### 9.4 连续消息合并窗口

同一用户连续发送多条时建议设置短暂静默窗口：

```text
新消息到达
→ 等待短暂窗口
→ 窗口内继续到达则合并
→ 达到最大等待上限后生成一次完整回复
```

具体等待时间通过配置和真实测试确定，不在设计文档中硬编码为平台固定值。

## 10. 上下文和知识库设计

### 10.1 身份归类

上下文键至少包含：

```text
platformCode + accountId + channelType + conversationId
```

不同平台同名用户默认不合并。评论和私信也默认分开保存；只有获得稳定平台用户 ID 并明确判断同一人时，才允许把评论摘要作为私信辅助背景。

### 10.2 “新消息”和“新话题”分开判断

```text
新消息：平台消息 ID 在数据库中不存在
旧消息：平台消息 ID 已存在

延续话题：语义上承接之前内容
新话题：当前提出不同业务问题
混合话题：同时包含旧话题追问和新问题
```

不能把“延续旧话题”误认为“旧消息”并跳过处理。

### 10.3 AI 上下文包

每次回复不发送全部历史，建议使用：

```text
最近 6～10 轮原始对话
+ 长期会话摘要
+ 用户已确认事实和偏好
+ 尚未解决的问题
+ 与当前问题相关的历史片段
+ 当前消息批次
+ 知识库命中结果
```

### 10.4 回答正确性保护

AI 只负责：

- 判断话题承接；
- 补全“那多少钱”等省略问题；
- 使用已召回知识组织自然回复；
- 标记无法确认的问题。

系统必须继续负责：

- 知识事实锁定；
- 多问题覆盖检查；
- 禁止知识库外编造；
- 低可信转人工；
- 回复长度和敏感内容校验；
- 发送目标绑定。

自动发送前应输出结构化检查结果：

```text
resolvedQuestions
unresolvedQuestions
knowledgeIds
contextUsed
conversationVersion
sendAllowed
```

## 11. 评论通道设计

评论通道与私信通道独立，但共用相同安全原则。

评论任务至少绑定：

```text
platformCode
accountId
videoId / postId
commentId
rootCommentId
parentCommentId
userId
sourceContent
```

回复前必须确认：

- 当前作品 ID 正确；
- 原评论 ID 唯一存在；
- 评论内容和发送者证据一致；
- 未检测到账号已有回复；
- 回复入口和输入框唯一；
- 发送后取得新增回复气泡或平台 ID。

评论列表重新排序、折叠或分页时，也不得依赖当前行号。

## 12. 页面与并发模型

### 12.1 推荐页面模型

每个平台账号推荐：

```text
一个登录 BrowserContext
├── 私信专用 Page
└── 评论专用 Page
```

B站等具备稳定消息 API 的平台优先使用 API 采集和发送，减少页面依赖。

### 12.2 锁范围

禁止使用覆盖整个账号的单一页面锁阻塞两个业务通道。建议锁键：

```text
{platform}:{account}:PRIVATE_MESSAGE
{platform}:{account}:COMMENT
```

同一私信会话再增加：

```text
{platform}:{account}:PRIVATE_MESSAGE:{conversationId}
```

共享的账号登录、验证码和平台风控状态仍由账号级控制器统一管理。

### 12.3 系统鼠标焦点限制

如果某个平台操作依赖操作系统鼠标、键盘和当前激活窗口，则两个页面不能真正同时点击。此时应：

- 优先改为基于指定 Playwright `Page` 和 DOM 元素操作；
- 或保留双队列、双页面，但对最终需要焦点的动作做极短的共享焦点调度；
- 不能让两个异步任务无锁争抢当前窗口。

## 13. 容量设计

目标日均规模：

```text
5 平台 × 每平台 30 私信 + 30 评论 = 300 事件/天
```

平均约：

```text
12.5 条/小时（按 24 小时）
25 条/小时（按 12 小时活跃期）
```

该规模不需要高并发集群。建议初始资源：

```text
浏览器页面操作并发：2～3
AI 生成并发：2～3
同一账号同一通道写操作：1
同一私信会话写操作：1
```

AI 仅在新消息、需要回复且通过规则过滤时调用。历史核对、重复消息和已人工处理消息不得调用 AI。

需要重点防止的不是容量不足，而是：

- SQLite 并发写锁；
- 浏览器页面相互跳转；
- 平台发送限速；
- 回复回执不确定；
- 采集失败后错误报告为空。

## 14. 平台适配建议

| 平台 | 私信/评论双通道 | 推荐实现 | 主要风险 |
|---|---|---|---|
| 抖音 | 支持 | 双 Page + 消息时间线核对 | 红点依赖、DOM 延迟、会话列表预览 |
| B站 | 支持，优先级高 | 消息 API 优先，页面做登录和补充核验 | API 参数、Cookie、账号身份 |
| 微信视频号 | 支持 | 私信页与评论页各一 Page | 登录过期、页面结构和会话 ID |
| 微博 | 支持 | 聊天页与评论通知页分离 | 聊天页和普通页结构差异 |
| 小红书 | 支持 | 主站评论页和私信页分离 | DOM 变化、回复入口唯一性、登录状态 |

所有平台必须实现统一适配器契约，但允许使用不同技术手段：

```text
API 优先
稳定 DOM 次之
低可信昵称匹配仅作人工辅助
```

## 15. Web 运行状态与告警

Web 必须分别显示每个平台、每个账号、每个业务通道：

```text
最后完整同步时间
最近扫描会话/评论数量
新增事件数量
待回复数量
正在处理数量
需要人工确认数量
同步不完整数量
最早待处理任务等待时间
最近错误码
```

禁止只显示：

```text
暂无私信
```

正确显示示例：

```text
抖音私信：同步完成，暂无新私信
最后完整同步：2026-08-24 14:32:18
```

或：

```text
抖音私信：同步未完成，系统正在重试
有 2 个会话无法确认加载完整
```

建议告警：

- 私信超过约定时限仍未进入数据库；
- 某通道连续多次同步不完整；
- `NEEDS_CONFIRMATION` 持续增加；
- 队列最老任务超过 SLA；
- 登录失效、验证码或账号身份不一致；
- 数据库锁冲突超过阈值。

## 16. 稳定性验收标准

“稳定回复”在本项目中定义为以下可验收结果，而不是“永远没有外部异常”。

### 16.1 采集标准

1. 有红点新消息能够采集；
2. 被人工提前读过的消息能够通过核对补采；
3. 会话打开期间到达的新消息能够被再次读取；
4. 服务重启后能够从旧检查点恢复；
5. 相同消息重复扫描只入库一次；
6. DOM 不稳定时不能报告空成功；
7. 历史补采消息不会触发批量自动回复。

### 16.2 发送目标标准

1. 列表重排后仍通过 conversationId 找到目标；
2. 同名用户不能串会话；
3. conversationId 不一致时自动发送次数必须为 0；
4. messageId 不存在或方向不明时自动发送次数必须为 0；
5. 回复发送后必须取得可靠平台证据才能标记成功。

### 16.3 并发标准

1. 私信和评论独立运行；
2. 私信异常不阻塞评论，评论异常不阻塞私信；
3. 同一会话严格串行；
4. 不同会话允许有限并行；
5. 用户补充消息使旧回复失效或进入下一批次；
6. 任务重启恢复后不重复发送。

### 16.4 内容标准

1. 上下文按稳定用户/会话 ID 隔离；
2. 当前问题和历史话题正确区分；
3. 多问题有覆盖结果；
4. 知识库没有答案时不编造；
5. 低可信答案转人工或请求澄清；
6. AI 不参与目标用户选择。

### 16.5 生产目标

在约定 300 条/天规模下，目标是：

```text
错目标自动发送：0
明确重复自动发送：0
静默漏采：0
不确定发送自动重试：0
同步失败错误显示为“暂无消息”：0
```

对外部平台故障无法承诺零故障，但必须做到可见、可重试、可恢复、可追踪。

---

## 17. 非目标和边界

第一阶段不做：

- 不做跨平台同一用户自动合并；
- 不依赖昵称构建永久用户身份；
- 不把全部历史记录每次发送给 AI；
- 不允许历史补采自动批量回复；
- 不允许回执不确定时自动重发；
- 不一次性对五个平台开放无人值守真实发送；
- 不为了追求速度取消稳定 ID 和发送前核验。

---

## 18. 最终结论

本方案不是单纯增加一个“消息队列”，而是建立一套完整的双通道事件处理系统：

```text
稳定身份
+ 完整消息事件账本
+ 私信/评论独立持久化队列
+ 每会话检查点
+ 同会话串行和连续消息合并
+ 三次时间线读取（进入会话、发送前、发送后）
+ 知识库约束和上下文记忆
+ 平台回执确认
+ 同步健康状态和自动修复
```

其中最关键的四句话是：

```text
红点只负责提醒。
消息 ID 负责判断新旧。
会话 ID 负责准确找人。
数据库队列负责确定处理顺序。
```

完成配套执行文档中的改造和真实平台验收之前，不能把本文描述的目标能力视为当前已经具备的生产能力。
